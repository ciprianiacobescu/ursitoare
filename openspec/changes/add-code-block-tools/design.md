## Decisions

1. **Seam and scope.** The `code_block` adapter, the `code` call kind, `checkAdapterSurface` (size, `effect_not_read`, `untrusted_result`, U+0000 and lone-surrogate refusals), the locked submit, `permit: null` and `adapter_unavailable` belong to `add-tool-adapters`. This unit adds the builder, the source check, the routes, the runner and the credential refusal, and restates no seam rule.
2. **The builder fixes what the admin cannot set (D20).** `codeBlockSurface` gives every tool effect `read`, `untrusted_result` false, `unsafe_to_retry` false and `call { kind: "code", source }`; `description` is present only when given (it changes the digest). A route body that names a fixed member is refused by its schema. A code block is `untrusted_result: false` because it is a pure function of its input: `producedTaint` gives such a block's output the INPUT taint, so an untrusted input yields an untrusted output and a trusted code block cannot launder taint. The scenario "An untrusted input gives an untrusted output at runtime" proves it on main's runtime path.
3. **The source check lives in `authoring`.** `codeSourceProblems` is the acorn wrap and return check of L1's `checkCodeSource`, as a pure function with no sink. L1 is not edited, so no validator layer gets stricter and `VALIDATOR_VERSION` stays (R5). Differences, by design: errors only (L1's `W_CODE_FORBIDDEN_API` warnings stay L1's; a forbidden API fails in the sandbox as `runtime_error`), and U+0000 or a lone surrogate in acorn's message (acorn quotes the offending character) becomes U+FFFD, so a response body is well-formed. A parity test runs both on ten sources. `tools` may not import `authoring` (module graph), so only the route calls it; `register.ts` relies on the seam for size, U+0000 and surrogates (`bad_value`).
4. **The runner mirrors the code node's call.** `createCodeRunner(sandbox)` reads the getter on every call, because `main` creates the pool after the invoke path (`let sandbox` is declared before `createInvokePath`, so `() => sandbox` sees the pool once it exists). A null pool is `INTERPRETER_NO_SANDBOX` (message `no sandbox is available for tool call of "<node>"`, node `ctx.nodeId`). Otherwise `run(call.source, args, CODE_LIMITS, { seed: codeSeed(ctx), nowIso: ctx.now.toISOString(), binding: "input", result: "object" })`: a rejection is the fault `sandbox_unavailable`, `{ ok: false }` its `fault.code`, a null value `output_invalid`, else `{ output: value }`. A fault is `INTERPRETER_TOOL_FAILED` (D20, D21), message `node execution failed`, `details` `{ stage: "code", fault }`. Only the fault code is copied (lesson t): the fault message, the source and the input reach no message or detail. The runner does not check the output; the block runtime checks it against the block's `output`.
5. **Routes.** `POST /api/v1/tool-registrations/code` (`respondIdempotent`; `{ id, tools }`, `tools` 1 to 100 of `{ name, description?, input, output, source }`, no other member) and `PUT /api/v1/tool-servers/:id/code` (`{ tools }`), action `register_tool_server`, session auth. Order: the body schema (`removeAdditional` and `allErrors` off: one error); `codeSourceProblems` per tool in index order, the first problem 400 `body/tools/<i>/source` with its message, before the transaction and the idempotency record; the seam inside the transaction (a source over the size, or with U+0000 or a lone surrogate in a string literal, parses and reaches it). Seam refusals map as the routes requirement of the spec says (the body is `{ id, tools }`, not a surface, so `mapToolsError` of `tool-server-routes.ts` does not fit; `kind_mismatch` can only mean a server of another adapter). `RECORD_SCHEMA` is a copy of the module-private one of `tool-server-routes.ts`; `engineKey` is kept by the seam's name and unused (no list route). The detail and list routes of `registerToolServerRoutes` serve a code-block server unchanged.
6. **Credential refusal.** A code-block server has no upstream: its origin `sandbox` fails `credential_ref.target_origin`, and the vault write comes first, so without a guard `provisionCredentialTx` would put a secret and then fail the insert. The guard reads `adapter` with `origin` and throws `CredentialsError` `CREDENTIALS_REFUSED` `{ reason: "no_credential_needed" }` after the input check and the server lookup, before any other query and any vault call. `CREDENTIALS_REFUSED` joins the credentials module's own union (not an API error code, D21); `apiErrorOf` maps it to 422 `OPERATION_REFUSED` and the route lists `OPERATION_REFUSED`. With no vault the route is still 503 first.
7. **main.** `createInvokePath` gets `code: createCodeRunner(() => sandbox)`; `registerCodeBlockRoutes` goes next to `registerToolServerRoutes`, after the lines U53 and U54 add. The invoke path exists only where `config.egress` is set (it needs a gateway), so a code block runs only there although its calls send nothing; no change.
8. **Harness and main's test.** A custom flow cannot run live in `invokeHarness` (`FlowKey` is fixed), but a dry run's reads go through `path.liveInvoker`, the invoke path a live run uses; so the live proof is a dry run of an all-read flow. `main` is the composition root no unit test drives through a code call (it needs egress, a durable runtime and a deployed policy), so its wiring is asserted by reading `src/main.ts` (U53's precedent) and by the document drift test; the getter's behaviour is proven by the runner rows.
9. **Rotation can correct the scheme and header (lens C11).** A credential stored with the wrong scheme or header could never be fixed: rotation took only `value`, there is no delete, and a second store is 409. `rotateCredential` gains an optional `change`; the resulting scheme and header are computed as the spec says and checked with `checkScheme`, the extracted scheme and header rules of `checkProvision` (same order, same reasons), after the row lock and before the vault put. The vault put already carries scheme and header on every call and replaces both (read: `vault.ts:154-156`, the fake `vault.ts:67-82`); the row update is what main forbids: the app role may update only `(key_version, rotated_at)`. Hence migration `0550_credential_scheme.sql`, one column grant (the CHECKs on scheme and header keep binding), and a MODIFIED base requirement. The audit payload gains `authScheme` and `headerName` only when a change is given (non-secret; the value is never recorded), so frozen payload assertions hold. Ruling D6a allows this third M7 migration and numbers it 0550 (U55, after U54's 0540); the alternative, a new server id, changes every block ref.

## Failure cases and security

- A null or closed pool, each fault class and a rejecting `run` have fixed details and no fault text. A refused source writes no server, no idempotency row and no audit row; a code-block credential writes no secret, row or event; a null route pool is 503.
- An input property named `url_host` makes every call of that tool `args_unconvertible` (`toCedarArgs` reserves it, as for any tool); this unit adds no rule for it. No gateway import (the three egress inventories stay), no service lookup, no token and no send for a code call (U47b's R1; the live scenario asserts it). The sandbox has no network and `CODE_LIMITS` (1 s, 32 MiB, 256 KiB stack, 1 MiB result). A code block still needs a grant (F9 step 4): an ungranted call is a `policy` deny with a decision row and no run of the code. The source is admin-written and its digest approved; a changed source drifts the server (U47b) but keeps the ref.

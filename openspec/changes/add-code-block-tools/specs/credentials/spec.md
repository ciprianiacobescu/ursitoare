## ADDED Requirements

### Requirement: A code-block server takes no credential
`provisionCredential` and `provisionCredentialTx` SHALL, after the check of the input and the lookup of the server (`CREDENTIALS_INVALID` and `CREDENTIALS_NOT_FOUND` first, as before) and before any other query and any vault call, throw `CredentialsError` `CREDENTIALS_REFUSED` with `details` `{ reason: "no_credential_needed" }` for a server whose adapter is `code_block`, and write no secret, no `credential_ref` row and no audit event. `CREDENTIALS_REFUSED` is a member of `CredentialsErrorCode` and not an API error code; `POST /api/v1/credentials` SHALL map it to 422 `OPERATION_REFUSED` `{ reason: "no_credential_needed" }` and list `OPERATION_REFUSED` among its errors. A fixture server SHALL provision as before.

#### Scenario: Provisioning for a code-block server is refused before the vault and a fixture server still provisions
- **WHEN** rows K1 to K5 and C1 of `test-plan-credentials.md` § Credential rows run with a recording vault writer
- **THEN** K1 and K2 (`provisionCredential` and `provisionCredentialTx`) throw `CREDENTIALS_REFUSED` `{ reason: "no_credential_needed" }` with 0 writer calls, 0 `credential_ref` rows and 0 `credentials.provisioned` events; K3 (value `""`) throws `CREDENTIALS_INVALID` `{ field: "value", reason: "size" }` and K4 (`ghost`) `CREDENTIALS_NOT_FOUND`; K5 (fixture server `acme`) answers its record after 1 writer call; row C1 of `test-plan-credentials.md` § Credential rows answers `POST /api/v1/credentials` for the code-block server with 422 `OPERATION_REFUSED` `{ reason: "no_credential_needed" }`, 0 vault calls and no `kv-secret-7f3a` in the body

### Requirement: A rotation can change the scheme and the header name, and records them without the value
`rotateCredential(deps, ctx, credentialId, value, actor, change?)` and `POST /api/v1/credentials/{id}/rotate` (body `{ value, authScheme?, headerName? }`, `authScheme` `API_KEY_HEADER` or `BEARER_TOKEN`, `headerName` 1 to 64 characters, no other member) SHALL, after `checkValue` and the row lock, take the resulting scheme `change.authScheme` or the row's, and the resulting header `change.headerName`, else the row's header when the scheme is `API_KEY_HEADER`, else NULL; check them with `checkScheme`, the rules of provisioning (`CREDENTIALS_INVALID` `{ field, reason }`: `authScheme` `bad_value`; `headerName` `required`, `bad_value`, `reserved`, `not_allowed`); put on the service with them (the vault replaces scheme and header on every put and counts the key version on); and then set `key_version`, `rotated_at`, `auth_scheme` and `header_name`. A refusal or a vault failure SHALL leave the row and the vault unchanged. The event `credentials.rotated` SHALL be `{ serviceId, keyVersion }` when `change` has no member and `{ serviceId, keyVersion, authScheme, headerName }` (the resulting values, `headerName` null for a bearer token) otherwise; the value SHALL reach no row, event, response or error. The route's `errors` are unchanged.

#### Scenario: A rotation changes the scheme and header, refuses a bad pair and a value-only rotation is as before
- **WHEN** rows S2 to S5 and Y1 to Y6 of `test-plan-credentials.md` § Rotation rows run with a recording writer, and rows Q1 to Q4 on the routes
- **THEN** S2 answers `authScheme` `BEARER_TOKEN`, `headerName` null, `keyVersion` 2, the fake holds that scheme with no header and the event payload is `{ serviceId, keyVersion: 2, authScheme: "BEARER_TOKEN", headerName: null }`; S3 and S4 answer their rows and payloads; S5 (value only) leaves the scheme and header and the payload `{ serviceId, keyVersion }`; Y1 to Y6 throw the code, field and reason of their rows and change no row, vault entry or event; Q1 is 200 with the S2 record, Q2 400 `body/headerName` `not_allowed`, Q3 400 `body/value` `must have required property 'value'`, Q4 403 for alice; no `kv-secret-8e2b` appears in any row, event, response or error

## ADDED Requirements

### Requirement: Fakes are checked against the flow's effect nodes and hooks before a run exists
`checkFakes(flow, catalogue, fakes)` SHALL require a non-empty entry list for every `write`, `send` or `pay` block node reachable from `start` over `augmentedSuccessors` and for every block hook of any reachable node, a `read` node included, whose block has one of those effects (key `hookMockKey`), because the stub decides from the effect of the context it is given and a hook context carries the hook block's own effect; and SHALL answer the problems sorted by `key` (UTF-16) then `index` (`null` first), at most 50, or the checked copy of `fakes`. A problem SHALL be `missing` (no or an empty list), `not_an_effect` (an existing node or hook that is no such block, a `read` included), `unknown_node` (no such node or hook), `schema` (an `output` that breaks the block's output schema; `detail` `<path> <keyword>`) or `shape` (an entry that is not `{ output }` or `{ error: { code, message } }` exactly as `checkMocks` judges it). It SHALL never throw.

#### Scenario: Missing, read, unknown, schema and shape problems
- **WHEN** `checkFakes` runs on the rows F1 to F13 and F12b of `test-plan.md` § checkFakes rows (`pay-once` and variants; `read-then-pay` variants for the hook rows of F12)
- **THEN** each row gives exactly the problems the table lists as `key index reason detail`, in order: F2 `pay null missing`, F5 `__proto__` then `ghost` `unknown_node`, F6 `pay 0 schema` `/ required`, F9 `flag` then `pay`, F10 exactly 50; a valid row returns a copy of its input; an unreachable effect node needs no fake (F8); the hook rows (F12) key the hook as `pay:post:notify`; in F12b the `pay` block hook `payhook` on the read node `lookup` is required when `lookup` is reachable (with `FK`, exactly `{ key: "lookup:post:payhook", index: null, reason: "missing", detail: "no fake entry" }`; with `{}` that problem then `pay`), is satisfied by a fake for `lookup:post:payhook`, and needs none on an unreachable read node; F13 gives one `"" null shape` problem and `fakes` `null`

### Requirement: The stub invoker reads live and answers every effect from its fake
`stubInvoker(live, fakes)` SHALL call `live.invoke` with the same call and context when `ctx.effect` is `read`; otherwise it SHALL answer a copy of the entry at index `ctx.attempt - 1` of `fakes[call.nodeId]`, or of `fakes["<nodeId>:<phase>:<hookId>"]` for a call with both `phase` and `hookId`, and SHALL NOT call `live.invoke`. A missing key, an exhausted list and an `{ error }` entry SHALL throw `INTERPRETER_TOOL_FAILED` (message `dry run <reason>`, node `call.nodeId`) with `details` `{ reason }` for `fake_missing`, `fake_exhausted` and `fake_error`, plus `hook` (the key) for a hook call and `fakeCode` (the entry's code, only when it matches `^[A-Za-z][A-Za-z0-9_.-]{0,63}$`) for `fake_error`; the entry's message SHALL NOT reach an error. `authorize` SHALL forward to the live invoker's and be present only when live has one. `dryRunInvokers(path, store, fallback)` SHALL, for mode `stub`, resolve an invoker over `await path.liveInvoker(run)` whose fakes are the payload of `run.mocksRef`, read once on the first `invoke`, and whose `authorize` forwards likewise, and SHALL throw `INTERPRETER_TOOL_FAILED` `{ reason: "fakes_unavailable" }` when the reference is `null`, the payload is no object or `getPayload` rejects (the details are exactly `{ reason: "fakes_unavailable" }`, the rejection's message and `code` are copied nowhere, nothing is sent and `live.invoke` is not called, and a failed load is not kept: the next call loads again); for any other mode it SHALL answer `fallback(mode, run)` and touch neither.

#### Scenario: A read goes live, an effect is answered by its fake and every failure has a fixed detail
- **WHEN** the rows T1 to T8 of `test-plan.md` § stubInvoker and dryRunInvokers rows (D1 to D5) run over a recording live invoker and `createMemoryRunStore()` (D5 over a store whose `getPayload` rejects once)

### Requirement: The dry-run endpoint starts a stub run as an author of the owner team
`POST /api/v1/flows/{flowId}/versions/{hash}/dry-run` SHALL be a `session` route of action `dry_run_flow` on the `Flow`, take the body `{ input, fakes }` (two objects, no other member, so no `run_as` and no `trigger`) and an optional `Idempotency-Key` with the semantics of the test endpoint, check `fakes` with `checkFakes` over the version's flow and the tenant catalogue, call `startRun` with `mode` `stub`, the checked fakes as `mocks`, `principal` `{ userId, kind }` and `actorChain` `[userId]`, and answer 202 `{ run }` with `toRunView`; the run SHALL carry trigger `test` and the fakes SHALL be its stored mocks payload.

### Requirement: The dry-run endpoint refuses the caller, the version and the fakes before a run exists
Once the authentication hook has passed (it needs the pool and the engine, so with no database it answers 503 `AUTHZ_UNAVAILABLE` first), the endpoint SHALL answer 503 `RUNS_UNAVAILABLE` when `enabled` is false, the pool is `null`, the interpreter is `null` or it has no durable runtime, before any other check of the handler; 404 `NOT_FOUND` for an unknown flow, tenant or hash; 403 `FORBIDDEN` for a caller outside the owner team's authors; 400 `VALIDATION_FAILED` with `details.fields` for a body outside the schema, for input outside the flow's inputs and, for `checkFakes` problems, one field `body/fakes/<key>` (`body/fakes/<key>/<index>` with an index, `body/fakes` for key `""`) with message `<reason>: <detail>`; and the `startRun` refusals as the test endpoint maps them; none SHALL create a run.

### Requirement: A dry run reads live and stubs every effect
A stub run SHALL be the production interpreter in mode `stub`: a `read` is authorised, recorded and sent through the invoke path, and each `write`, `send` or `pay` is authorised and recorded by the policy point, has its intent recorded in mode `stub` and is answered by its fake with no token and no request. A denial SHALL fail the run `INTERPRETER_TOOL_DENIED`, and a fake `{ error }` SHALL fail the node `INTERPRETER_TOOL_FAILED` with `reason` `fake_error`.

#### Scenario: read-then-pay makes one live call, no pay call, and records both permits
- **WHEN** with the harness of `test-plan-runs.md` (`G_LOOKUP` and `G_PAY` deployed) alice dry-runs `read-then-pay` with `{ vendor_name: "Acme GmbH", amount: 12.5 }`, first with `fakes` `{}` and then with `FK2`, and the run is executed
- **THEN** the first post is 400 `[{ field: "body/fakes/pay", message: "missing: no fake entry" }]` with no run and no tool call; the second is 202 and the run ends `completed` at `done` with output `{ payment_id: "PAY-1" }`; the fake tools hold exactly one call (`lookup`) and none for `erp.create_payment@1`; the fake egress issued 1 token and forwarded 1 request; the `pay` intent is `done` in mode `stub`; two `allow` decisions are recorded, `lookup` (reasons `[G_LOOKUP.id]`, permit V1) and `pay` (reasons `[G_PAY.id]`, permit V2, `bodyDigest` `D_PAY`), as steps 3 to 5 of the plan list

### Requirement: main wires the stub invoker and enables the route only when egress is configured
When `config.egress` is set and the durable branch runs with a policy runtime (a database and role `all` or `worker`, so `runtime !== null`), `main` SHALL build the gateway, the tool directory, the service resolver and a principal loader (`getUser` and `loadMemberships`; a missing or disabled user is `null`), create the invoke path over the policy runtime, give the interpreter `invokerFor` = `dryRunInvokers(path, store, testRunInvokers(store))` and register the dry-run route with `enabled` true. Without `config.egress`, `invokerFor` SHALL stay `testRunInvokers(store)` and the route, always defined, SHALL have `enabled` false. With `config.egress` set and no database, `main` SHALL build none of those objects and no interpreter, so dry runs are unavailable as without a database: the route stays defined with `enabled` true and a request is refused with 503 `AUTHZ_UNAVAILABLE` by the authentication hook of every `session` route (`src/api/route.ts:174-181`, which needs the pool and the engine), before the handler's own 503 `RUNS_UNAVAILABLE` could apply. `invokerFor("live")` SHALL stay refused in both cases.

#### Scenario: Egress wires the stub invoker and the route; its absence leaves both off
- **WHEN** `main` starts with the test database and no `egress`, then with `egress` (`test-plan-runs.md` rows M1 and M2; row M3: `egress` and no database), and alice posts a dry run for `pay-once` with `FK` each time in M1 and M2 and an anonymous caller posts it in M3
- **THEN** without egress the route is defined, the post is 503 `RUNS_UNAVAILABLE` and `invokerFor("stub")` and `("live")` reject `INTERPRETER_NO_INVOKER`; with egress the post is 202, `invokerFor("stub")` resolves to an invoker with `invoke` and `authorize`, `("live")` still rejects `INTERPRETER_NO_INVOKER`, and the run ends `failed` with `INTERPRETER_TOOL_DENIED` at `lookup`, `details` `{ reason: "tool_unbound" }`; with `egress` and no database the route is defined, the anonymous post is 503 `AUTHZ_UNAVAILABLE`, `bindInterpreter` is never called (no interpreter, so no invoke path and no stub invoker) and `checkEgress` ran once

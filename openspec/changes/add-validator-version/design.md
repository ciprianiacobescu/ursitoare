## Context

Validators get stricter over time, and a stored `validated` version is never re-checked: it keeps running under rules it would now fail. This unit stores which validator produced each validation, refuses a non-draft version validated by an older one when a run starts (D5, binding rule R5), and ships the first stricter rule: a node id has at most 128 characters, the length the run store, the effect intents and the decision log already enforce.

## Decisions

1. **Layout, no edge change.** `version.ts` has no import. `schema.ts`, `l1.ts` and `format/refs.ts` import it inside `authoring` (`refs.ts` reaches into `../validate/version.ts`, a same-module import). `registry` already imports `authoring` (`validate.ts:2`); `api` already imports `registry` (`test-run-routes.ts:8`); `interpreter` gains only a type member. `MODULES` is unchanged.
2. **Refuse, do not re-validate (D5).** Re-validating inside `startRun` would need the catalogue and a registry write the interpreter does not own, and would run silently on every start. The author re-validates with the existing route; that is the only way back, and the round trip is proved (scenario "Stale versions are refused by both routes until the author validates again").
3. **Where `stale` is decided and read.** `isValidationStale` is pure. `registryVersionLoader` reads `validatorVersionOf` in the loader's transaction (the `withTenantTx` that runs `getVersion`) and spreads `stale: true` into the record only when stale (lesson z: the frozen `C-771f9778` deep-equals the record of a current version). `startRun` is the only reader. `executeRun` (`execute.ts:142`) and the invoke path (`path.ts:75`) load the same record and never read `stale`, so a run queued before its version went stale still executes: the refusal is at start only. The stale check sits after the draft check and before the kind, block and input checks, so a stale version reports only that (rows S5, S6).
4. **Stamp only a passing validation (ruling on question 2).** `validateVersion` writes `validator_version` in the one `UPDATE` it already runs, as `CASE WHEN <result.ok> THEN VALIDATOR_VERSION ELSE validator_version END`, so the stamp, the result and the time cannot disagree and a failing validation leaves the column as it was. Why: only a `draft` or `validated` version drops to `draft` on failure (`validate.ts:41-43`); a `tested`, `reviewed`, `published` or `deprecated` version keeps its state. Stamping a failure would make that version current, so it would run although it fails the current validator, the hole this unit closes. The column therefore records the validator that last passed the version, a drop to `draft` keeps the old number (a draft is never stale), and the hole is proved by rows H0 to H4. Not covered here, carried to M11 (U77): a version whose latest validation failed and whose stamp is current from an earlier pass.
5. **Upgrade consequence.** Migration 0275 adds the column NULL and no backfill: a backfill would claim validator 2 checked rows it never saw. So every non-draft version stored before this change is refused at run start until one `POST .../validate`. That is the intended effect and the first deploy shows it; the draft rows are unaffected.
6. **Migration and privilege.** `0275_validator_version.sql`: `ALTER TABLE ursitoare.flow_version ADD COLUMN validator_version integer CHECK (validator_version IS NULL OR validator_version >= 1);` and `GRANT UPDATE (validator_version) ON TABLE ursitoare.flow_version TO ursitoare_app;`. The only existing grant on the table beyond `SELECT, INSERT` is `UPDATE (state, validation, validated_at)` (`0270_flow_registry.sql:40`, and no other migration names `flow_version`), so the app role gains one more column, never a table-level update. The base requirement ("no delete and no update of a version's text or hash") stays true and no base scenario lists the updatable columns, so the requirement is ADDED, not MODIFIED. `migrate` applies every file not in the ledger in file order (`migrate.ts:268-273`), so 0275 applies on a database that already holds 0495 (read, not run: `withTestDatabase` applies all files in order).
7. **The bound.** `$defs.nodeId` is `^[a-z][a-z0-9_]{0,127}$`, built from `MAX_NODE_ID_LENGTH` (`{0,${MAX_NODE_ID_LENGTH - 1}}`), so one constant drives L1 and `refs.ts`. `start`, every `next`, `on_timeout`, `default`, every `cases` value and every `nodes` key inherit it through `ref("nodeId")` (`schema.ts:81-244`). Only the `propertyNames` branch of `schemaErrors` gets the new message, for a key that matches the old pattern and is longer than 128; `/start`, `next` and the rest show Ajv's `must match pattern` text, and every other failure keeps its text. No code is added (`FLOW_ERROR_CODES` stays at 47).
8. **The hook `nodes` selector does not route through `$defs.nodeId`** (checked, as the planner could not confirm): L1 accepts `hooks` as `{ type: "array", items: { type: "object" } }` (`schema.ts:89`), and layer H validates a `nodes` entry as a string that is a key of the flow's `nodes` (`hooks/check.ts:66-73`; `when.from` and `when.next` through `checkSelector`, `:108`). Layer H runs only after L1 to L3 gave no error (`validate.ts:52-68`), and every key has passed the bound, so an entry cannot name a longer id: a 129-character node never reaches H (K2) and a 129-character entry no node has is `H_SCHEMA` (K3). No explicit pattern is added and `check.ts` is not edited (it is not in this unit's file list). Question 1.
9. **Left alone.** `src/grants/compile.ts:10`, `src/interpreter/hooks/actions.ts:7` and `web/src/app/features.ts` keep their unbounded patterns (D22: they never accept new ids from outside); the `suspiciousInterpolation` heuristic (`refs.ts:145`) only warns; the web grants client is U56's. Frozen L1 tests: no fixture has a node id over 128 characters (a grep of `src`, `test`, `web/src`, `e2e` and `docs` for `[a-z][a-z0-9_]{128,}` finds only hex strings in vault tests), and the whole frozen suite ran green with the bound (§ Verification).
10. **Grants.** `NODE_PATTERN` becomes `^[a-z][a-z0-9_]{0,127}$`; `SCOPE_SCHEMA` is shared by the create body and every grant response, so the document gains the bound five times. A grant stored earlier with a node id over 128 characters can exist (`grant.node_id` is unbounded, `0490_grants.sql:9`); nothing creates one after. That the list route still serializes such a row is inferred (Fastify does not check `pattern` on responses), not run (UNVERIFIED).
11. **`types.ts` is shared.** U47b, first in plan order, edits `CallAuthorization.permit`; this unit adds only `readonly stale?: true` to `LoadedVersion` after re-reading the file at that time. `exactOptionalPropertyTypes` is on, so a loader cannot assign `undefined`: the member is present only when stale.
12. **OpenAPI.** Regenerated with `pnpm run test test/support/openapi-docs.ts`; `C-d150bfa4` compares it with the served text. U53 to U55 regenerate it after this unit.

## Failure cases and security

- A NULL, a missing row and a number below `VALIDATOR_VERSION` are all "not current" for a non-draft state (fail closed); a number at or above it is current, so a rollback of the engine to an older build leaves rows stamped by a newer validator runnable.
- The loader's extra read runs in the loader's transaction (the `withTenantTx` that runs `getVersion`); a failure rejects the load as before (`startRun` and `executeRun` already handle a load rejection).
- The refusal creates no run and calls no `enqueue`; its `details` is the ASCII word `validation_stale`, storable as `jsonb`.
- `validator_version` is a number the app role writes only through `validateVersion`; a viewer cannot make a version look current: `POST .../validate` runs the validator and stamps in one transaction.
- No API error code, interpreter code, action or dependency is added (D21): the route answer reuses `OPERATION_REFUSED` with the existing `cause` member.

- Rule R5: every later stricter validator change bumps `VALIDATOR_VERSION` in its own unit (roadmap cross-cutting rule, added in the same push as these specs); this unit's bound is the first, so 2 is the first bump from 1 (every validation stored before it).

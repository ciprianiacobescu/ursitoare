## ADDED Requirements

### Requirement: A tenant is created by name with its review profile
`ensureTenant(pool, { name, reviewProfile }, opts?)` SHALL, on a pool connected as `ursitoare_owner`, return the tenant called `name` and whether this call created it: it SHALL create it with the given profile when no tenant has that name, whatever other tenants exist, return the existing one with `created: false` when its profile is the same, and refuse with `TENANT_PROFILE_CONFLICT` and change nothing when its profile differs. `findTenantByName(pool, name)` SHALL return the tenant context of that name or `null`. Both SHALL refuse an invalid name with `TENANT_INVALID` before any query.

#### Scenario: Create, repeat, conflict, bad input and race
- **WHEN** on a migrated database with `opts` `{ ids: sequentialIds(), clock: fixedClock("2026-11-25T10:00:00Z") }`, `ensureTenant(db.ownerPool, { name: "Acme", reviewProfile: "team" }, opts)` runs twice, then with `reviewProfile` `solo`; then `seedTwoTenants(db)` runs and `ensureTenant` runs with "Beta" and `solo`; then with the names `""`, `" x"` and 201 `x` characters, with the profile `gold`, and as `db.appPool` with "Zed"; then eight concurrent calls with "Race" and `solo`, each with its own `sequentialIds(100)`; and `findTenantByName(db.ownerPool, ...)` runs with "Tenant A", "Ghost" and `""`
- **THEN** the first call returns `{ tenant: { tenantId: "ten_00000000-0000-7000-8000-000000000000", reviewProfile: "team" }, created: true }` and the repeat the same tenant with `created: false`; the `solo` call rejects with `TENANT_PROFILE_CONFLICT` (message `the tenant exists with another review profile`, `details` `{ reviewProfile: "team" }`) and the row keeps `team`, `name` `Acme` and `created_at` `2026-11-25T10:00:00.000Z`; "Beta" returns `{ tenant: { tenantId: "ten_00000000-0000-7000-8000-000000000001", reviewProfile: "solo" }, created: true }` and the table then holds four rows, the seeded ones unchanged; the three bad names and the bad profile reject with `TENANT_INVALID`, adding no row; the app-role call rejects with `TENANT_BOOTSTRAP_FAILED` (`details.sqlstate` `"42501"`) and adds no row; of the eight concurrent calls exactly one has `created: true`, all eight return one `tenantId`, and one `Race` row exists; `findTenantByName` returns `{ tenantId: "tenant_a", reviewProfile: "solo" }`, then `null`, then rejects with `TENANT_INVALID`

### Requirement: The sink tokens bind as two hash-only routes
`bindSinkTokens(pool, ctx, tokens)` SHALL register, in one tenant transaction, the broker token as a route of kind `mintkey_sink_broker` and the proxy token as a route of kind `mintkey_sink_proxy` for the tenant `ctx`, resolve `{ broker, proxy }` with `"created"` or `"exists"` for each, store only `sha256` of each token, refuse equal tokens with `TENANT_INVALID`, and keep no route of a call that fails, including a call whose token another tenant already holds (`TENANT_ROUTE_CONFLICT`). `MINTKEY_SINK_ROUTE_KINDS` SHALL be `{ broker: "mintkey_sink_broker", proxy: "mintkey_sink_proxy" }`, frozen.

#### Scenario: Bind, repeat, resolve and roll back
- **WHEN** after `seedTwoTenants(db)`, `bindSinkTokens(db.ownerPool, a, { broker: "tok-broker-A1", proxy: "tok-proxy-A1" })` runs twice; then with the proxy `tok-proxy-A2`; then for `b` with `{ broker: "same", proxy: "same" }`; then for `b` with `{ broker: "tok-broker-B1", proxy: "tok-proxy-A1" }`; then for `{ tenantId: "ghost", reviewProfile: "solo" }` with `{ broker: "g1", proxy: "g2" }` and for `a` with `{ broker: "", proxy: "p" }`; and `resolveTenantBy(db.appPool, kind, token)` runs for `("mintkey_sink_broker", "tok-broker-A1")`, `("mintkey_sink_proxy", "tok-proxy-A1")`, `("mintkey_sink_proxy", "tok-broker-A1")` and `("mintkey_sink_broker", "tok-broker-B1")`
- **THEN** the first call resolves `{ broker: "created", proxy: "created" }`, the repeat `{ broker: "exists", proxy: "exists" }`, the third `{ broker: "exists", proxy: "created" }`; the equal tokens reject with `TENANT_INVALID` and add no row; the call that takes `tok-proxy-A1` rejects with `TENANT_ROUTE_CONFLICT` (message `route is already registered`, holding neither token) and leaves no route for `tok-broker-B1`; the ghost tenant rejects with `TENANT_UNKNOWN` and the empty token with `TENANT_INVALID`; the resolves give `tenant_a`, `tenant_a`, `null`, `null`; the table of routes holds exactly three rows for `tenant_a` (one broker, two proxy), every `key_hash` equals `hashRouteKey` of its token, and no row holds `tok-` as text; `MINTKEY_SINK_ROUTE_KINDS` is frozen with the two kinds above

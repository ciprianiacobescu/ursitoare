## ADDED Requirements

### Requirement: Fakes are checked against the flow's effect nodes and hooks before a run exists
`checkFakes(flow, catalogue, fakes)` SHALL require a non-empty entry list for every `write`, `send` or `pay` block node reachable from `start` over `augmentedSuccessors` and for every block hook of any reachable node, a `read` node included, whose block has one of those effects (key `hookMockKey`), because a hook context carries the hook block's own effect; and SHALL answer the problems sorted by `key` (UTF-16) then `index` (`null` first), at most 50, or the checked copy of `fakes`. A problem SHALL be `missing` (no or an empty list), `not_an_effect` (an existing node, or a block hook whose block is no write, send or pay, a `read` included), `unknown_node` (no such node or block hook; the key of a `code` hook is one, as `checkMocks` judges it), `schema` (an `output` that breaks the block's output schema; `detail` `<path> <keyword>`) or `shape` (an entry that is not `{ output }` or `{ error: { code, message } }` exactly as `checkMocks` judges it). It SHALL never throw.

#### Scenario: Missing, read, unknown, schema and shape problems
- **WHEN** `checkFakes` runs on the rows F1 to F14 and F12b of `test-plan.md` § checkFakes rows (`pay-once` and variants; `read-then-pay` variants for the hook rows of F12)
- **THEN** each row gives exactly the problems its table lists as `key index reason detail`, in order; a valid row returns a copy of its input (F1); an unreachable effect node needs no fake (F8); in F12b the `pay` hook `payhook` on the read node `lookup` is required when `lookup` is reachable (with `FK` exactly `lookup:post:payhook null missing`; with `{}` that problem then `pay`), is satisfied by its own key and needs none on an unreachable node; F13 gives one `"" null shape` problem and `fakes` `null`; F14 gives `lookup:post:detour null unknown_node`

### Requirement: The stub invoker reads live and answers every effect from its fake
`stubInvoker(live, fakes)` SHALL call `live.invoke` with the same call and context when `ctx.effect` is `read`; otherwise it SHALL answer a copy of the entry at index `ctx.attempt - 1` of `fakes[call.nodeId]` (`fakes["<nodeId>:<phase>:<hookId>"]` for a call with `phase` and `hookId`) without calling `live.invoke`. A missing key, an exhausted list and an `{ error }` entry SHALL throw `INTERPRETER_TOOL_FAILED` (message `dry run <reason>`, node `call.nodeId`) with `details` `{ reason }` for `fake_missing`, `fake_exhausted` and `fake_error`, plus `hook` (the key, only when it matches `^[\x21-\x7e]{1,256}$`) for a hook call and `fakeCode` (the entry's code, only when it matches `^[A-Za-z][A-Za-z0-9_.-]{0,63}$`) for `fake_error`; the entry's message SHALL NOT reach an error. `authorize` SHALL forward to the live invoker's and be present only when live has one. `dryRunInvokers(path, store, fallback)` SHALL, for mode `stub`, resolve an invoker over `await path.liveInvoker(run)` whose fakes are the payload of `run.mocksRef`, read once on the first `invoke`, and whose `authorize` forwards likewise; a `null` reference, a payload that is no object or a rejecting `getPayload` SHALL throw `INTERPRETER_TOOL_FAILED` `dry run fakes_unavailable` (node `null`, details exactly `{ reason: "fakes_unavailable" }`, the rejection's message and `code` copied nowhere, nothing sent, `live.invoke` not called, a failed load not kept); a rejecting `path.liveInvoker(run)` SHALL reject the resolver with `dry run live_unavailable` (details exactly `{ reason: "live_unavailable" }`, nothing of the rejection copied); for any other mode it SHALL answer `fallback(mode, run)` and touch neither.

### Requirement: The dry-run endpoint starts a stub run as an author of the owner team
`POST /api/v1/flows/{flowId}/versions/{hash}/dry-run` SHALL be a `session` route of action `dry_run_flow` on the `Flow`, take the body `{ input, fakes }` (two objects, no other member, so no `run_as` and no `trigger`) and an optional `Idempotency-Key` with the semantics of the test endpoint, check `fakes` with `checkFakes` over the version's flow and the tenant catalogue, call `startRun` with `mode` `stub`, the checked fakes as `mocks`, `principal` `{ userId, kind }` and `actorChain` `[userId]`, and answer 202 `{ run }` with `toRunView`; the run SHALL carry trigger `test` and the fakes SHALL be its stored mocks payload.

### Requirement: The dry-run endpoint refuses the caller, the version and the fakes before a run exists
Once the authentication hook has passed (it needs the pool and the engine, so with no database it answers 503 `AUTHZ_UNAVAILABLE` first), the endpoint SHALL answer 503 `RUNS_UNAVAILABLE` when `enabled` is false, the pool is `null`, the interpreter is `null` or it has no durable runtime, before any other check of the handler; 404 `NOT_FOUND` for an unknown flow, tenant or hash; 403 `FORBIDDEN` for a caller outside the owner team's authors; 400 `VALIDATION_FAILED` with `details.fields` for a body outside the schema, for input outside the flow's inputs and, for `checkFakes` problems, one field `body/fakes/<key>` (`body/fakes/<key>/<index>` with an index, `body/fakes` for key `""`) with message `<reason>: <detail>`; and the `startRun` refusals as the test endpoint maps them; a rejection of `loadVersion` or `catalogueFor` is not caught by the handler and answers 500 `INTERNAL` without the rejection's text; none SHALL create a run.

### Requirement: A dry run reads live and stubs every effect
A stub run SHALL be the production interpreter in mode `stub`: a `read` is authorised, recorded and sent through the invoke path; each `write`, `send` or `pay` is authorised and recorded by the policy point, has its intent recorded in mode `stub` and is answered by its fake with no token and no request. A denial SHALL fail the run `INTERPRETER_TOOL_DENIED`, and a fake `{ error }` of a node call SHALL fail the node `INTERPRETER_TOOL_FAILED` with `reason` `fake_error`. A block hook SHALL be stubbed by its own effect, whatever its node's effect is (`blockHookRunner` gives the invoker a context whose `effect` is the hook block's; `delivered-shapes.md`), so a `pay` or `send` hook on a `read` node reaches no tool; its fake `{ error }` is the hook runner's `HOOK_ERROR` `tool_failed`, or with `on_error: continue` a failed entry and the node goes on.

#### Scenario: read-then-pay makes one live call, no pay call, and records both permits
- **WHEN** with the harness of `test-plan-runs.md` (`G_LOOKUP` and `G_PAY` deployed) alice dry-runs `read-then-pay` with `{ vendor_name: "Acme GmbH", amount: 12.5 }`, first with `fakes` `{}` and then with `FK2`, and the run is executed

### Requirement: The principal loader gives an active user's entity and nothing for anyone else
`createPrincipalLoader(pool)` (`src/api/principal-loader.ts`, type `PrincipalLoader` of add-tool-invocation) SHALL answer, for a tenant context and a user id, `{ tenantId: ctx.tenantId, userId, kind, roles, teams }` with `kind` the user's (`human` or `service`) and `roles` and `teams` the sorted lists of `loadMemberships`, as `resolvePrincipal` builds a session principal (`src/identity/rbac/principal.ts:9-27`), and `null` for a user that is missing, of another tenant or `disabled`; it keeps no cap of its own on the lists (`resolvePrincipal` throws above 64, `principal.ts:9-27`; the engine's `isPrincipalEntity` bound is `src/pdp/principal.ts:17-18,51`; no row, it needs 65 memberships); a malformed id SHALL reject (`getUser` refuses it, `src/identity/users.ts:150-158`), which the invoke path maps to `INTERPRETER_TOOL_FAILED` `{ stage: "authorize" }`.

### Requirement: main wires the stub invoker and enables the route only when egress is configured
When `config.egress` is set and the durable branch runs with a policy runtime (a database and role `all` or `worker`), `main` SHALL build the gateway, the tool directory, the service resolver and `createPrincipalLoader(pool)`, create the invoke path over the policy runtime, give the interpreter `invokerFor` = `dryRunInvokers(path, store, testRunInvokers(store))` and register the dry-run route with `enabled` true. Without `config.egress`, `invokerFor` SHALL stay `testRunInvokers(store)` and the route, always defined, SHALL have `enabled` false. With `config.egress` set and no database, `main` SHALL build none of those objects and no interpreter, the route has `enabled` true and a request is refused 503 `AUTHZ_UNAVAILABLE` by the authentication hook of every `session` route (`src/api/route.ts:186-188`, which needs the pool and the engine), before the handler's own 503; with a database and role `api` it likewise builds none of them, the hook passes and the handler answers 503 `RUNS_UNAVAILABLE`. `invokerFor("live")` SHALL stay refused in every case.

#### Scenario: Egress wires the stub invoker and the route; its absence leaves both off
- **WHEN** `main` starts with the test database and no `egress`, then with `egress` (`test-plan-runs.md` rows M1 and M2; row M3: `egress` and no database; row M4: `egress`, a database and role `api`), and alice posts a dry run for `pay-once` with `FK` each time in M1 and M2 and an anonymous caller posts it in M3
- **THEN** without egress the route is defined, the post is 503 `RUNS_UNAVAILABLE` and `invokerFor("stub")` and `("live")` reject `INTERPRETER_NO_INVOKER`; with egress the post is 202, `invokerFor("stub")` resolves to an invoker with `invoke` and `authorize`, `("live")` still rejects, and the run ends `failed` `INTERPRETER_TOOL_DENIED` at `lookup` with `{ reason: "tool_unbound" }`; with `egress` and no database the anonymous post is 503 `AUTHZ_UNAVAILABLE`, with a database and role `api` alice's is 503 `RUNS_UNAVAILABLE`; in both `bindInterpreter` is never called

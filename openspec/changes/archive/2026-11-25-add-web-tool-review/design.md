## Context

The engine discovers MCP tools, records the server's claims as `call.hints` (R3a) and reports each tool it leaves out (R4); U56 gives the registration and credential pages. This unit lets the admin drive discovery and see what she approves. Rulings: D17, R3, R3a, R4, R6.

## Decisions

1. **Files.** New: `web/src/tools/review.ts`, `ReviewSections.tsx` (the sections "Discovery" and "Changes" and the table "Calls", as U56's `CredentialSection.tsx`) and tests; edited (task 3.1): `ServersPage.tsx` (the detail effect, :101-117, and one `<ReviewSections` after U56's sections in the root `div`, :214). The sections have their own file because main pins `ServersPage.tsx` to one `className="tools-feedback"` and one `data-tone="primary"` (`web/src/tools/tools-pages-restyle.test.ts:35-46`, `:87-88`). No feature file. No `.tsx` imports CSS (`web/src/ui/rules-tree.test.ts:44-56`): `ReviewSections.tsx` uses kit `Section`, `DataTable` and `Button` (tone secondary, the default), the kit classes `ui-field` and `ui-input`, token utilities (no palette utility, hex or inline style) and the existing `.tools-feedback` rules (`tools.css:41-55`); `tools.css` is unchanged (it has no `.tools-section`). No `servers.ts` change (U56 design 2) and **no `messages.ts` change**: `toolsErrorMessage` is pinned to 13 reasons and `registerMessages` throws for a code with two texts (U56 design 5); `discoveryErrorText` owns the discovery texts and falls back to it.
2. **One detail read.** `loadServerReview` replaces `loadToolServer` in the page's detail effect: the same `ToolServerView` beside the two raw surfaces, so the page reads the detail once per load (the M6 browser tests count reads) and no view member is added (lesson z).
3. **Reading (R3, R4).** `parseReviewTools` follows `servers.ts`: own members only, at most 100 tools with unique names `^[a-z][a-z0-9_]{0,63}$`, exactly one of `http` (`method`, `path` of 1 to 16 and 1 to 2,048 characters) and `call`, no kept string with U+0000 to U+001F or U+007F. A `call` is `http` (`method` `GET`, `POST`, `PUT`, `PATCH` or `DELETE`, `path` 1 to 1,024 characters, `params` of `{ name, in: "path" | "query" }`, boolean `body`), `mcp` (`endpoint` 1 to 1,024, `name` `^[A-Za-z0-9_.-]{1,128}$`, one of U47b's four `protocolVersion`, `output` `structured` or `text`, optional `hints` whose present `readOnly`, `destructive`, `idempotent` are booleans, other members ignored) or `code` (`source` 1 to 65,536 characters without U+0000); else the surface is `null`: one the engine never writes is unreadable, not half shown. `call` is `<method> <path>` for `http` and an `http` call, `mcp <name> (<protocolVersion>)`, `code (<n> characters)`; `hints` reads `read-only`/`not read-only`, `destructive`/`not destructive`, `idempotent`/`not idempotent`, in that order, joined by `, `, else `—`. Nothing in `review.ts` derives an effect, `untrusted_result` or `unsafe_to_retry` from it (R3: only the overlay does).
4. **The diff** is the digest's view: members compared with the digest's defaults (`description` and `data_class` null, `untrusted_result` true, `unsafe_to_retry` false), `input`, `output`, `hints` and the `http` or `call` (without `hints`) by canonical JSON (keys sorted at every depth), `untrusted_fields` sorted; names sorted by code unit. `hints` is its own field, so a hint change alone reads `changed find_vendor: hints`; `untrusted_fields` keeps a digest change from reading as an empty diff. Descriptions reach agents (tool poisoning), so the admin reads them (D17a, C7): a description change carries both full texts in `SurfaceChange.description`; an `added` tool carries its description and its described input properties (`input.properties`, top level), and so does a `changed` tool whose `input` changed (the new side). An absent approved surface compares as no tools, so the first approval lists every tool as `added` with these lines: the card's text "No approved surface to compare." is gone for that reason. `changesView` shows each text as plain text (React escapes it), neutralised (C6) and bounded as the spec says. A `description` that is not a string makes the surface unreadable.
5. **Discovery is stateless (D17), effects pre-filled (D17a).** The overlay travels in each request. "Discover tools" posts `discoverBody(initialDraft(tools))` over the tools of the approved surface (`{ tools: {} }` before any approval), so a rediscovery does not reset the admin's effects to `write`; a tool not in the approved surface is left to the proposal (`""`). The settings table starts from the pending surface (`initialDraft`), so "Discover again with these settings" keeps its effects and names. The overlay set here is `{ effect?, name?, skip? }` (C9: a tool name, to resolve a collision, and "Skip", to leave a tool out); a `name_collision` refusal stores no surface, so the table then lists the colliding names of `details.names` (`collidingNames`) and the admin names one. Every lookup by a server tool name uses `Object.hasOwn`, and an entry `__proto__` is not sent, so it defaults (m2). A tool the server no longer lists does not fail the rediscovery (D17b): `mcpSurface` skips its overlay entry and reports it in `excluded` as `not_listed`, which `discoveryText` shows as "Left out: gone_tool (not_listed)", and the diff reads `removed gone_tool`. A tool skipped earlier is not in the approved surface, so "Discover tools" proposes it again (it shows as `added`); "Discover again with these settings" keeps the skip. Each click draws a fresh `crypto.randomUUID()` key (a replayed key would answer from storage).
6. **Read note (D17a, U53 design 4).** A `read` makes a dry run call the real tool (U51; D14 says the same for MCP): `readNote` is a fixed sentence under "Calls" when any tool is `read`, else `null`; the Effect column says which.
7. **Errors.** A 422 `OPERATION_REFUSED` reason or a 503 `EGRESS_UNAVAILABLE` reason has the text of test-plan.md § Calls and errors (the engine's message is not shown); any other error is `toolsErrorMessage`. For `no_tools` the tools left out are listed (R4); `name_collision` lists the names; `discovery_failed` with status `401` or `403` says the stored credential was refused (C9); `credential_missing` adds that a server needing no key still needs a value (m4). `too_many_tools` (more than 100 tools) falls back to the kit text: it stores no surface, so there is no table to "Skip" tools in (an API overlay; a limit of this unit).

## Roles and names

**Server detail** (`/admin/tool-servers?server=<id>`, the flex column of `ServersPage.tsx:214`), after the region "Surface" (:236), U56's "Credential" and, when shown, its "Change registration" (so the order is Surface, Credential, Change registration, Discovery, Changes, Calls). "Discovery" and "Changes" are kit `Section`s and "Tool settings" and "Calls" `DataTable`s with the caption visible (each differs from the `h1` "Tool servers", `captionDisplayFor`); a composed text (`changed x: effect, call`, a Calls cell) is never split: a `Badge` may wrap the whole text, none wraps a part of it (the journey matches each as one string); no new link or button is named like a navigation label or the home links "Review pending tool servers" and "Deploy grant changes", or holds "Ursitoare" (strict mode). An MCP server has a region named by `h2` "Discovery": the button "Discover tools"; a `p` `role="status"` or `role="alert"` (its own `ActionPhase`, reset with the server id); with `serverName` tools in the pending surface, the table "Tool settings" (kit `DataTable`; columns "Server tool", "Server hints", "Tool name", "Effect"; per row a text `input` and a plain `select`, named as the spec says, "Proposed" having the value `""`; after a `name_collision` refusal the rows are the colliding names) and the button "Discover again with these settings"; the draft resets on each loaded detail. Every server has a region named by `h2` "Changes" with a `ul` named "Changes" (one `li` per item, its text then one `p` per line) or a `p` with the `changesView` text, and the table "Calls" (`DataTable`; `callRows` of the pending surface, else the approved one; columns "Tool" (row header), "Call", "Effect", "Retry", "Result", "Server hints"; empty title "No calls"; an unreadable surface shows "The surface could not be read."), then a `p` with `readNote` when not `null`.

export function surfaceDiff(approved: unknown, pending: unknown): SurfaceChange[];   // by tool name, sorted by name
export function changeText(c: SurfaceChange): string;   // "added x" | "removed x" | "changed x: effect, call"
export function changesView(approved: unknown, pending: unknown): { text: string | null; items: { text: string; lines: string[] }[] };   // (addition); an absent approved surface counts as no tools; lines: descriptions and described input properties, neutralised, cut at 2,000 characters (D17a, C6, C7)
export interface DiscoverDraft { effects: Readonly<Record<string, "" | "read" | "write" | "send" | "pay" | "skip">>; names?: Readonly<Record<string, string>> }   // key: server tool name; "" = proposal; names, "skip": additions (C9)

export function discoverBody(d: DiscoverDraft): { tools: Record<string, { effect?: string; name?: string; skip?: true }> };

## Failure cases and security

- Server text (tool names, left-out names, hints) is React text only; a left-out name is neutralised the same way and cut to 80. Descriptions (old, new, first approval, input properties) show as plain text, neutralised and bounded as in decision 4; React escapes them, no raw HTML.
- A hostile discovery answer (an unreadable `server`, `era` `dual`, 1,001 left-out entries) is `INVALID_RESPONSE`; an overlay key `__proto__` is an own key (`Object.fromEntries`). No secret is handled. No endpoint, action, error code or migration is added; discovery needs `register_tool_server`, which the page's gate already requires.

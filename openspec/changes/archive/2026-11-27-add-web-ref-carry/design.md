## Context

A ref is `<server id>.<tool name>@N` (`src/tools/surface.ts:80-100`: the lowest `N` whose stored hash is the tool's hash). Approving a changed tool gives it `@N+1`; grants keep naming `@N`, and a new grant is pending until a deploy (`src/grants/policy-sets.ts:279-301`). `GET /grants` has no tool filter (`src/api/grant-routes.ts:274-280`) and no superseded status exists (`src/grants/status.ts`), so the web derives everything from the three routes it already has.

## Decisions

1. **Files and page edits.** New: `ref-carry.ts` (all logic), `RefCarryPanel.tsx` (notice, button, list, link), `RefMarker.tsx`. The `.tsx` files are separate because frozen source rows pin the pages (`ServersPage.tsx`: one `tools-feedback`, one `data-tone="primary"`, one `<ConfirmDialog`, no `useId`, no `loadToolServer(`, and after U56d `surface={` once; `GrantsPage.tsx`: no `data-tone="primary"`, no `people/`, one `tools-feedback`). `ServersPage.tsx` edits, by anchor text: an import of `RefCarryPanel` before `import { ReviewSections }`; imports of `approvedEffects`, `changedRefs` and `type RefChange` before `import { loadServerReview }`; `const [carry, setCarry] = useState<{ changes: RefChange[]; run: number } | null>(null);` after `const [action, setAction]`; `setCarry(null);` last in the `[serverId]` reset effect; in `confirmApprove`, `const before = view;` and `setCarry(null);` before `setDialogOpen(false);`, and `await approveToolSurface(...)` becomes `const after = await ...` followed, when `before !== null`, by `setCarry((held) => ({ changes: changedRefs(before, after, approvedEffects(approvedSurface)), run: (held === null ? 0 : held.run) + 1 }))`; one JSX line before `{dialog === null || !dialogOpen ? null : (`, `<RefCarryPanel key={carry.run} changes={carry.changes} />` when `carry !== null`. None touches the `const servers = useMemo(` block, whose deps are now `[reloadKey]` (main 71defd22): the list reloads after an approve, and the stubbed `tool-servers` list answers again. `GrantsPage.tsx`: `createApiClient` added to the `../api/client.ts` import, two more imports, `const [servers, setServers] = useState<readonly ToolServerView[]>([])`, one `useEffect` after the blocks read calling `loadAllToolServers(createApiClient(), controller.signal)`, and `<RefMarker state={refState(grant.tool, servers)} />` after `grantTextWithBadge(grant)` inside the same `<span id=...>`. `parseGrant`, `grantBody`, `grantRowText` and `servers.ts` are not edited.
2. **The load-bearing fact (read, and run in a scratch copy of main).** A drifted detail parses to the pending surface's tools carrying the approved refs by name (`servers.ts:150-168`; `src/tools/store.ts:159-183`). The approve answer is a record without surfaces (`src/api/tool-server-routes.ts:109-114`), built after the new blocks are imported (`src/tools/store.ts:447-562`), so its refs are the new ones: `changedRefs(view before, approve answer)` names exactly the bumped tools. The effects are the exception (D49): a drifted detail's `tools[].effect` is the pending surface's, equal to the answer's, so the old effect is read from the raw approved surface of the same detail (`ServersPage` has it as `approvedSurface`, `review.ts:665-687`) through `approvedEffects`, which uses `parseReviewTools` (`review.ts:175`); an unreadable surface gives an empty map and the before view's effect. A first approval has `ref: null` before and gives `[]`, so the frozen approve tests are unchanged. A tool added or removed has no counterpart and is not listed.
3. **`refState`.** A server id and a tool name hold no `.`, so the text before the first `.` and the text up to the last `@` are the two parts; the answer is `null` unless a listed, non-pending server lists that tool with a non-null ref. The catalogue ref `crm.find_customer@1` next to the MCP server `crm` (`e2e/test_m7_tools.py:186`; `test/support/catalogue/blocks.v0.json:45`) gets no marker, nor do refs with no dot, extra dots or an unlisted server. Residual: a catalogue block named like a listed tool reads as that tool's old ref (a block has no source in the API). A drifted server's list item carries the approved surface's tools (no surfaces in the record), so its equal ref is `waiting`. Lookups use a `Map` or `find`.
4. **Reads.** `loadAll*` use `cursorPageFetcher` (a bad page or item rejects, nothing is skipped), `limit` 100, at most 100 pages. The Grants page reads `GET /tool-servers` with `createApiClient()`, not `browserSession.api`: only the latter has a session-end handler (`web/src/auth/session-fetch.ts:47-72` turns a 401 `UNAUTHENTICATED` into a redirect to sign-in), and the frozen no-sign-in Grants tests (`e2e/test_m6b_admin.py:384`, `:448`; `e2e/test_m6b_section_layout.py:69`, `:81`) answer `/blocks` and `/grants` and leave `/tool-servers` to the real engine, which answers 401 without a session (`src/api/route.ts:205-208`, read, not run). Success sets the list; a failure is dropped: no marker, no loading state, no alert (W7). The route needs `register_tool_server` (`src/api/tool-server-routes.ts:220-226`): `deploy_policy` alone gets 403 and no marker.
5. **The copy.** Nothing is requested before the press. A press runs `carryGrants`: all grants are read, `copyPlan` picks the non-revoked grants on an old ref, and each `any_step` one is posted in order with its own key, except that a grant on a tool whose effect changed (D49: a `read` grant would grant payment rights on a tool that became `pay`) is never posted, whatever its scope, and gets a line saying to grant it again; a refusal (`arg_unknown`, `tool_unknown`, `role_unknown`: `src/grants/store.ts:183`, `:253-263`) is a line and the loop goes on. A node-scoped grant is never posted: one made before the flow names the new ref fingerprints the old node and turns `needs_reconfirm` (`src/grants/store.ts:265-274`), so its line says to update the flow first. Keys come from `carryKeys(() => crypto.randomUUID())` held for the life of the panel, so a second press re-sends the same key and body and the engine replays the stored answer instead of creating a duplicate (`src/api/idempotency.ts:106-216`). The next approval mounts a new panel (`key={carry.run}`). Nothing is revoked or edited.
6. **Texts.** `REF_CARRY_NAMES` holds the card's six values plus `deployPath` "/admin/policies", `effectChanged`, `none` and `listName` (test-plan.md § Names). `{grant}` is `grantLabel`; `{to}` and `{tool}` are the new ref. `fillRefText` is one pass with a function replacer, so `$&` inside a value stays literal. After a press the panel shows the list "Copied grants" (when it has lines), the `empty` and `incomplete` notes and, only when `deploy` is true, the link "Deploy on Policies" (otherwise nothing is pending).
7. **The marker and the pins.** `RefMarker` is a plain `span` with `data-slot="ref-marker"`, `data-state`, Badge's radius and padding and token classes (`bg-warning-surface text-warning-text` superseded, `bg-info-surface text-info-text` waiting). It is not a `[data-slot="badge"]` element, so the row-scoped locators at `e2e/test_m6b_admin.py:453`, `:458` still find one; it follows the status `Badge` in the same cell, so `grantRowText` and the pinned substrings hold. With no marker every Grants row is byte-equal to base; the panel is absent unless `changedRefs` gives a change. It uses `tools-note`, never `tools-feedback`; its only `alert` is `ErrorPanel` for a failed read, and a new approval clears it, so one `alert` and one `status` per scope hold.

## Failure cases and security

- The grants read fails (403 without `deploy_policy`, 5xx, an unreadable item): `carryGrants` rejects before any `POST`, the panel shows `ErrorPanel`, nothing is created. A `POST` that fails, is refused or answers without a readable id becomes one "Not created for <grant>: <reason>." line (an unreadable id reads `INVALID_RESPONSE`; the grant may exist) and the loop goes on; an unusable key is `request_failed` with no request. Over 10,000 grants, the first 10,000 are read and "Only the first 10,000 grants were read." follows the list. An empty plan shows "No grant names the old refs." and posts nothing.
- A shown `reason` is a lowercase word from a 422 `OPERATION_REFUSED`, else an upper-case error code, else `request_failed`: server text never reaches the page as free text. No secret, endpoint, action, audit event or migration is touched; the new grants are ordinary `POST /grants` calls checked by `deploy_policy` and pending until a deploy.

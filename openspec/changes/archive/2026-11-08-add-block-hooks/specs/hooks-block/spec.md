## Purpose

Block hooks call a catalogue tool before or after a node as steps of their own, through the node's `ToolInvoker` and effect gate with keys of their own, and a SIGKILL at any hook step leaves one effect per key.

## ADDED Requirements

### Requirement: Mock keys, block refs and hook values are pure and fixed
`hookMockKey(nodeId, placement)` SHALL equal `hookStepName(nodeId, placement)`; `hookBlockRefs(flow)` SHALL list, sorted and without duplicates, the `uses` of every `block` hook of the nodes and of the flow rules, skipping malformed entries; `resolveHookValue(value, scope, hook)` SHALL equal `resolveValue` for every root but `hook`, and resolve `hook.input`, `hook.output`, `hook.node`, `hook.next` and `hook.from` by `Object.hasOwn` path walk into a copy, failing `INTERPRETER_REF_UNRESOLVED` (`details.ref`) for a null root or a missing key.

### Requirement: A block hook is its own step and calls its tool as a hook
`blockHookRunner.run` SHALL resolve `hook.with` with `resolveHookValue` from the hook context, check it against the block's input schema, and call `services.invoker` with `{ tool, args, nodeId, effectSeq: site.slot, phase, hookId: placement.label }`, plus `generation: attempt - 1` only when `hctx.attempt` is above 1, and the context `{ ...step, attempt: hctx.attempt, effect: def.effect, unsafeToRetry: def.unsafe_to_retry === true, idemKey: null, hook: { phase, label } }`. A `read` hook SHALL be one step `site.stepName` whose value is the `HookRun`; any other effect SHALL run `effects.before` and the invoker (not on `reuse`) in `site.stepName` and `effects.after` in `attemptStepName(hookStepName(nodeId, placement) + "#done", hctx.attempt)` (`pay:post:notify#done`; `pay:post:notify#done:r2` at attempt 2, as U42 names `send#done:r2`), whose value is the `HookRun`, with the invoker context carrying the decision's `idemKey`. Both SHALL check the output against the block's output schema, answer `{ outcome: { action: "continue" }, entry }` with `kind` `block`, `fused` false, `action`, `mutated`, `to` and `error` null, `tool` the block and `idemKey` the decision's (null for `read`), and a replay over the recorded values SHALL call nothing.

### Requirement: A failing block hook fails the node, or with on_error continue is recorded and skipped
A failure of the invoker, the gate, the input or output schema or an unresolved reference SHALL throw `HOOK_ERROR` (message `block hook "<label>" failed (<reason>)`, `node` the wrapped node, `details` `{ hook: hookStepName(nodeId, placement), reason }`) with `reason` `tool_failed`, `input_invalid`, `output_invalid` or `args_unresolved`, and no text of the tool or gate error; with `on_error: "continue"` the same failures SHALL be recorded inside the step as a completed value and answered as `{ outcome: { action: "continue" }, entry }` with `state` `failed`, `error` `{ code: "HOOK_ERROR", message: "block hook failed (<reason>)" }` and the `idemKey` the gate had issued (else null), the node going on. An `unknown` decision (`effect_unknown`) and a missing block (`block_missing`) SHALL throw whatever `on_error` says, so no later retry fires over an unknown effect. At `hctx.attempt` above 1 a hook whose block's effect is `pay` SHALL throw `HOOK_ERROR` (`reason` `effect_retry`) before `effects.before`, whatever `on_error` says, so a retried node never pays again (X1); a `send` hook still runs there. The seven reasons: `tool_failed`, `input_invalid`, `output_invalid`, `args_unresolved`, `block_missing`, `effect_unknown`, `effect_retry`.

### Requirement: A hooked version runs in a mock test run with its own keys
`loadValue` SHALL load the blocks of `hookBlockRefs(flow)` with those of the nodes, so a block named only by a hook is runnable; a mock run of a version with a block hook SHALL need a mock under the hook key, answer the hook call from it, and key the hook's intent `idemKey(tenant, lineage, nodeId, slot, attempt - 1)`, which differs from the node's key and from every other hook of the node.

### Requirement: A kill at a hook step leaves one effect per key
With the crash harness, a SIGKILL after a step function has returned (`after:<step>`) SHALL leave the effect of that step done and its result not recorded, and after the restart the step SHALL run again under the same key while every recorded step is replayed without a call: a node's own step (`after:pay`), a post block hook's step (`after:pay:post:notify`) and the first step of a retried attempt (`after:send:r2`) each give one effect per key.

### Requirement: The format document teaches a solo author to run code and hooks
`docs/authoring/format.md` SHALL hold one section `## Running code and hooks` that contains these nineteen lines, each exactly once and in this order, as whole lines (one sentence for each code semantic, for the hook body and its limits, for the meaning of each outcome, the two lines of what each phase allows, which are the outcomes of `add-hook-runtime`'s action matrix, and four lines of `add-hook-checker`'s bounds, retry scope and route rule; `test-plan.md` § Format section quotes the source of each):

```
- A code node body reads its input as `input`.
- A code node body must return an object.
- A code node body is pure: it does no I/O.
- A code node body sees a clock frozen to the run's step time.
- A code node body sees a seeded `Math.random`.
- A code node body runs under `CODE_LIMITS` (1000 ms, 32 MiB).
- A code hook body reads `ctx` and returns nothing or an object with an `action`.
- A code hook body runs under `HOOK_LIMITS`, the same 1000 ms and 32 MiB.
- `continue` lets the node go on; a pre-hook may replace its input and a post-hook its output.
- `skip` lets a pre-hook answer with the node's `output`, so the node does no work.
- `redirect` lets a post-hook send the run to a node of its `routes` instead of the node's successor.
- `retry` lets a post-hook run the node and its post-hooks again as the next attempt, without its pre-hooks, up to `max_retries`.
- `fail` lets a pre-hook or a post-hook fail the node and the run with its `reason`.
- A pre-hook may return: continue (with input), skip (read block or code node only), fail.
- A post-hook may return: continue (with output on a code or block node), redirect (from a code, switch, wait or block node, to a node in routes, never an effect node), retry (with max_retries; an effect node needs allow_effect_retry; never on pay), fail.
- A node has at most 16 pre-hooks and 16 post-hooks, a flow at most 16 rules, and a hook or rule id at most 64 characters.
- `max_retries` is an integer from 1 to 5, set only on a post code hook.
- A retry never re-pays: `max_retries` is refused (`H_RETRY_SCOPE`) on a `pay` node and when the node's post-hooks hold a `pay` block hook, and a `send`, `write` or unknown-effect node or post block hook needs `allow_effect_retry: true`.
- A hook route into a node of effect `write`, `send`, `pay` or unknown (an agent, a subflow) is refused (`H_ROUTE_EFFECT`).
```

The terms of the frozen `doc-terms.test.ts` SHALL stay named.

#### Scenario: The format document has the section for running code and hooks
- **WHEN** `docs/authoring/format.md` is read after the edit and `missingDocTerms` runs on it
- **THEN** the heading `## Running code and hooks` occurs exactly once; its section (up to the next `## `) contains the literal strings `CODE_LIMITS`, `HOOK_LIMITS`, `16 hooks`, `16 rules`, `64 characters`, `allow_effect_retry`, `H_RETRY_SCOPE` and `H_ROUTE_EFFECT`, and also `1000 ms`, `32 MiB`, `ctx` and each of `continue`, `skip`, `redirect`, `retry` and `fail`; the lines of the section that equal any of the nineteen lines of the requirement are exactly those nineteen, in that order (so a deleted, reworded, added, duplicated or reordered line fails), among them, as whole lines, the two lines beginning `- A pre-hook may return:` and `- A post-hook may return:`, each exactly once; `missingDocTerms` returns `[]`

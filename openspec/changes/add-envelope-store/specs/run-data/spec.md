## Purpose

The run-data store keeps what a run did, per tenant: the run row, one row per step attempt, content-addressed payloads and an event log, behind repositories and two `RunStore` implementations (database and in-memory) with one contract.

## ADDED Requirements

### Requirement: Run tables are tenant tables with narrow privileges
Migration `0310_run_data.sql` SHALL create `ursitoare.run`, `ursitoare.step_execution` (partitioned by day on `run_day`), `ursitoare.envelope_payload` and `ursitoare.event` (partitioned by month on `time`), each tenant-leading with forced row-level security and, if partitioned, a DEFAULT partition, and SHALL grant the app role no delete and no update of a key, identity or payload column.

#### Scenario: Objects, isolation and privileges
- **WHEN** tenant A has `run` `r_1`, a step of it (node `n1`, `seq` 0, `run_day` `2026-10-25`), an `envelope_payload` row and an `event` row, inserted by the app role; the app role as A, each in its own transaction, updates `run.flow_hash`, deletes from `run`, updates `envelope_payload.data`, deletes from `event`, updates `step_execution.seq`, then updates `run.state` and `step_execution.state`, inserts a `run` with `mode` `dry`, a step with `attempt` 0 and a step (node `n2`, same run and day) with `seq` 0; as B it counts the four tables' rows and inserts an `event` with `tenant_id` `tenant_a`
- **THEN** `to_regclass` finds the four tables, `ursitoare.step_execution_default` and `ursitoare.event_default`, and the ledger holds version 310 named `run_data`; `relrowsecurity` and `relforcerowsecurity` are true for all four; `step_execution` and `event` have `relkind` `p` and comments `partition: day` and `partition: month`; the first five statements reject with `{ code: "42501" }`, the two state updates succeed; the `dry` and `attempt` 0 inserts reject with `{ code: "23514" }`, the `n2` step with `{ code: "23505" }`; B counts 0 rows in each table and its insert rejects with `{ code: "42501" }`; `checkTenancyCatalog` returns `[]`

#### Scenario: Rows land in the daily and monthly partitions
- **WHEN** `ensurePartitions(db.ownerPool, { now: () => new Date("2031-03-15T00:00:00Z") })` has run; as A, steps of `r_1` with `seq` 0, 1, 2 have `run_day` `2031-03-31`, `2031-04-01`, `2019-06-01`, and events `ev_1`, `ev_2`, `ev_3` have `time` `2031-03-31T23:59:59Z`, `2031-04-01T00:00:00Z`, `2019-01-01T00:00:00Z`
- **THEN** `tableoid::regclass::text` of the steps in `seq` order is `ursitoare.step_execution_p20310331`, `ursitoare.step_execution_p20310401`, `ursitoare.step_execution_default`, and of the events in `event_id` order `ursitoare.event_p203103`, `ursitoare.event_p203104`, `ursitoare.event_default`; `ursitoare_app` has neither `SELECT` nor `INSERT` on any of these six leaves

### Requirement: Payloads are content-addressed by their canonical JSON
`payloadDigest` SHALL return the lowercase hex SHA-256 of a value's canonical JSON (object keys sorted by UTF-16 code units, no whitespace, UTF-8) and refuse a value that is not plain JSON with `RUN_DATA_INVALID`; `envelopeStore.put` SHALL store each canonical value once per tenant under that digest and refuse a canonical form over 1,048,576 bytes with `RUN_DATA_TOO_LARGE`.

#### Scenario: Canonical JSON and the digest
- **WHEN** `payloadDigest` gets `{ b: 1, a: [true, null] }`, the same keys in the other order, `null`, `{}`, `{ b: 1, aa: 2 }`, `{ "\uFF5E": 1, "\u{1F600}": 2 }`, `-0`, `1e21` and an array nested 64 deep; and, each alone, `NaN`, `undefined`, a function, `10n`, `new Date(0)`, `"a\u0000b"`, `"\uD800"`, `{ "k\u0000": 1 }`, an array nested 65 deep, an object holding itself, and `{ note: "secret-input", bad: NaN }`
- **THEN** the first two return `51705a2c9eb3e7e410a58f696a770c3ac3885a0cf43eb7fc88f5e47c11d4d30d`; `null` returns `74234e98afe7498fb5daf1f36ac2d78acc339464f950703b8c019892f982b90b`, `{}` returns `44136fa355b3678a1146ad16f7e8649e94fb4fc21fe77e8310c060f61caaff8a`; the next four return the SHA-256 (computed in the test with `node:crypto`) of the UTF-8 texts `{"aa":2,"b":1}`, `{"😀":2,"～":1}`, `0` and `1e+21`; the 64-deep array returns 64 lowercase hex characters; each value of the second list throws a `RunDataError` with `code` `RUN_DATA_INVALID`, and the last message does not contain `secret-input`

#### Scenario: The envelope store keeps each value once per tenant
- **WHEN** in tenant A `envelopeStore.put` gets `{ b: 1, a: [true, null] }`, the same keys in the other order, `{ "\uFF5E": 1, "\u{1F600}": 2 }`, a string of 1,048,574 `a` characters, one of 1,048,575, and `NaN`; `get` gets the digest of the first value, that of the `\uFF5E` object, 64 zeros and `"ABC"`; tenant B calls `get` with the first digest, then `put` with the first value
- **THEN** the first two puts return `{ sha256: "51705a2c9eb3e7e410a58f696a770c3ac3885a0cf43eb7fc88f5e47c11d4d30d", size: 23 }` and A holds one row with it; the 1,048,574-character string returns `size` 1048576; the 1,048,575-character one rejects with `RUN_DATA_TOO_LARGE` and stores no row, `NaN` with `RUN_DATA_INVALID`; `get` of the first digest returns `{ sha256, mediaType: "application/json", size: 23, data: { a: [true, null], b: 1 }, pinned: false }`, and for it and for the `\uFF5E` object `payloadDigest(data)` equals `sha256`; the zero digest gives `null`, `"ABC"` rejects with `RUN_DATA_INVALID`; B's `get` gives `null`, and after B's put each tenant holds one row of that digest

### Requirement: A run is created once and moves only along the states a transition allows
`runRepository.create` SHALL store a `queued` run with its input and mocks as payload references and answer the stored row when the `runId` exists; `runRepository.transition` SHALL change a run only while its state is in `from`; `runRepository.list` SHALL page a tenant's runs newest first.

#### Scenario: Create is idempotent and validated
- **WHEN** `create` gets `NEW_RUN("r_1", { mocks: { lookup: { status: "ok" } } })` at `2026-10-25T23:59:59.500Z`, then `NEW_RUN("r_1", { input: { other: true }, flowId: "rf-2" })` at `2026-10-26T08:00:00Z`; two connections create `r_2` at once; and each alone: `runId` `bad id`, `mode` `dry`, an `actorChain` of 33 entries, `input` `NaN`, an invalid `at`
- **THEN** the first returns a record with the identity fields of `NEW_RUN`, `state: "queued"`, `inputRef` and `mocksRef` equal to `payloadDigest` of the input and the mocks, `runDay: "2026-10-25"`, `createdAt: "2026-10-25T23:59:59.500000Z"`, and `outputRef`, `error`, `terminalNode`, `startedAt`, `endedAt` null, and `envelopeStore.get` finds both payloads; the second returns a record deep-equal to the first and stores no payload for `{ other: true }`; both concurrent calls return one record and `run` holds one `r_2`; each invalid call rejects with `RunDataError` `RUN_DATA_INVALID` and `run` holds exactly `r_1` and `r_2`

#### Scenario: A transition applies only from the listed states
- **WHEN** `r_1` is `queued` and `transition` gets, with `T1` to `T5` at 09:00:01 to 09:00:05 on 2026-10-25: `{ state: "running", from: ["queued"], at: T1 }`, the same again, `{ state: "running", from: ["queued", "running"], at: T3 }`, `{ state: "completed", from: ["running"], at: T4, output: { verdict: "approve" }, terminalNode: "end_ok" }`, `{ state: "cancelled", from: ["queued", "running"], at: T5, output: { late: true } }`, `from: []`, and an unknown `runId`; running `r_4` gets `{ state: "failed", from: ["running"], at: T4, error: { code: "FLOW_FAILED", message: "node classify failed", node: "classify" } }`; running `r_5` gets `completed` and `cancelled` (both `from: ["running"]`) at once on two connections; `state: "done"`, `from: ["bogus"]`, an `error` with `code` `""` and an invalid `at` are each tried alone
- **THEN** in order: `running` with `startedAt` `2026-10-25T09:00:01.000000Z`; `null`, the row unchanged; the row with `startedAt` unchanged; `completed` with `endedAt` `2026-10-25T09:00:04.000000Z`, `terminalNode: "end_ok"` and `outputRef` `payloadDigest({ verdict: "approve" })`, whose payload `get` returns; `null`, the row still `completed` and no payload for `{ late: true }`; `null`; `null`; `r_4` is `failed` with that `error`; exactly one concurrent call returns a record and the stored state equals its `state`; the four bad inputs reject with `RUN_DATA_INVALID`

#### Scenario: List pages newest first and applies the filter
- **WHEN** tenant A holds `r_a` (09:00:00, `rf-1-core`, team `finance`, `u_alice`, `completed`), `r_b` (09:00:01, `rf-1-core`, `finance`, `u_bob`, `running`), `r_c` (09:00:01, `rf-2`, `ops`, `u_dave`, `queued`), `r_d` (09:00:02, `rf-1-core`, `finance`, `u_alice`, `queued`) and tenant B holds `r_e` (09:00:03); `list` runs with `filter` `{ sql: "true", values: [] }` and `limit` 2, then with that `next` as `after`; then, with that filter and `limit` 10, with `flowId` `rf-1-core` and with `state` `queued`; with `limit` 10 and `filter` `{ sql: "owner_team = ANY($7) OR principal_user_id = $8", values: [["ops"], "u_alice"] }`; and each alone `limit` 0, `after` `{ createdAt: "not a time", runId: "r_a" }`, `flowId` `Bad Id`
- **THEN** page 1 is `["r_d", "r_c"]` with `next` `{ createdAt: "2026-10-25T09:00:01.000000Z", runId: "r_c" }`, page 2 `["r_b", "r_a"]` with `next` null; the `flowId` query gives `["r_d", "r_b", "r_a"]`, the `state` query `["r_d", "r_c"]`, the filter query `["r_d", "r_c", "r_a"]`, none holds `r_e`; `RUN_LIST_FILTER_FIRST` is 7; the three bad queries reject with `RUN_DATA_INVALID`

### Requirement: A step is one row per attempt key
`stepRepository.upsert` SHALL store a step under (run, node, `effectSeq`, `turn`, `attempt`, `generation`) in the day partition of its run, so that recording the same key again updates that row and keeps its `seq` and `startedAt`; `stepRepository.list` SHALL return a run's steps by `seq` with an exclusive `afterSeq` cursor.

#### Scenario: A step is recorded once per key, in its run's day
- **WHEN** `r_1` was created at `2026-10-25T23:59:59.500Z`; `upsert` gets `STEP("r_1", "classify", 0, { input: { vendor: "acme" }, startedAt: 2026-10-25T23:59:59.600Z })`; then the same key with `state` `completed`, `output` `{ verdict: "approve" }`, `outcome` `approve`, `taint` `["untrusted"]`, `policyDecisionId` `pd_1`, `idemKey` `ik1_` plus 64 `b`, `seq` 7, `startedAt` `2026-10-26T00:00:05Z`, `endedAt` `2026-10-27T00:00:00Z`; `attempt` 2 of `classify` with `seq` 1; node `route` with `seq` 1; a step of `r_missing`; and each alone `nodeId` `Bad-Node`, `attempt` 0, `state` `done`, a `taint` label `""`
- **THEN** the first returns the input's key and `kind`, `seq: 0`, `state: "started"`, `inputRef` `payloadDigest({ vendor: "acme" })`, `startedAt: "2026-10-25T23:59:59.600000Z"`, `taint: []` and null `outputRef`, `outcome`, `error`, `policyDecisionId`, `idemKey`, `endedAt`; the second returns that key with `state: "completed"`, `outputRef` `payloadDigest({ verdict: "approve" })`, `outcome: "approve"`, `taint: ["untrusted"]`, `policyDecisionId: "pd_1"`, the `idemKey`, `seq: 0`, the first `startedAt` and `endedAt: "2026-10-27T00:00:00.000000Z"`, in one row with `run_day::text` `2026-10-25`; attempt 2 is a second row with `seq` 1; `route`, the step of `r_missing` and the four invalid steps reject with `RUN_DATA_INVALID`, leaving 2 rows for `r_1`

#### Scenario: Steps page by seq and a payload belongs to the runs that reference it
- **WHEN** `r_1` (input `I1`, mocks `M1`, output `O1`) has steps `a`, `b`, `c`, `d` with `seq` 0 to 3 written in the order 2, 0, 3, 1, where `c` has input `SI` and output `SO`; `r_2` has a step with input `{ secret: "r2-only" }`; `stepRepository.list` runs for `r_1` with `{ limit: 2 }`, `{ limit: 2, afterSeq: 1 }`, `{ limit: 10, afterSeq: 3 }`, `{ limit: 0 }`, for `r_unknown`, and as tenant B for `r_1`; `envelopeStore.referencedBy` gets `r_1` with the digests of `I1`, `M1`, `O1`, `SI`, `SO`, `{ secret: "r2-only" }` and an unstored value, `r_unknown` with `I1`'s digest, and `r_1` with `"xyz"`
- **THEN** the pages hold `seq` `[0, 1]` with `next` 1, `[2, 3]` with `next` null, and `[]` with `next` null; `limit` 0 rejects with `RUN_DATA_INVALID`; `r_unknown` and tenant B give `{ steps: [], next: null }`; `referencedBy` is true for the first five, false for `{ secret: "r2-only" }` (although stored), the unstored digest and `r_unknown`, and `"xyz"` rejects with `RUN_DATA_INVALID`

### Requirement: An event is appended once and never changed
`appendEvent` SHALL insert one row into `ursitoare.event` and ignore an event with the same `eventId` and `time`.

#### Scenario: Events are appended and a replay is ignored
- **WHEN** in tenant A `appendEvent` gets `{ eventId: "ev_1", runId: "r_1", correlationId: null, type: "run.cancelled", data: { by: "u_alice" }, time: AT }`, the same again, the same `eventId` one second later, and `{ eventId: "ev_2", runId: null, correlationId: "corr-1", type: "run.created", data: {}, time: AT }`; and each alone `eventId` `bad id`, `type` `Run Cancelled`, `data` `NaN`, an invalid `time`, and `data` a string of 1,048,575 `a` characters
- **THEN** `event` holds three rows for A: `ev_1` at `AT` with that `data`, `ev_1` one second later, and `ev_2` with `run_id` null and `correlation_id` `corr-1`; the replay returns without error; the four invalid events reject with `RUN_DATA_INVALID`, the large one with `RUN_DATA_TOO_LARGE`; tenant B sees no event

### Requirement: Every repository call checks its transaction's tenant
Every function of `runRepository`, `stepRepository`, `envelopeStore` and `appendEvent` SHALL reject with `RUN_DATA_INVALID` when its transaction was opened for another tenant than `ctx`, and `createRunStore` SHALL never return or change another tenant's rows.

#### Scenario: Two tenants never see each other's run data
- **WHEN** through `createRunStore(db.appPool)` A creates `r_1` with input `{ who: "a" }`, B creates `r_1` with `{ who: "b" }`, each records step `n1`, and A moves its `r_1` to `running`; B calls `getPayload` with the digest of `{ who: "a" }`, and both list `r_1`'s steps; and in `withTenantTx(db.appPool, b, ...)` with context A the functions `runRepository.create`, `get`, `list`, `transition`, `stepRepository.upsert`, `list`, `envelopeStore.put`, `get`, `referencedBy` and `appendEvent` are called
- **THEN** A's `getRun("r_1")` has `inputRef` `payloadDigest({ who: "a" })` and `state: "running"`, B's has `payloadDigest({ who: "b" })` and `state: "queued"`; B's `getPayload` of A's digest is `null`; each lists only its own step; all ten mismatched calls reject with `RUN_DATA_INVALID`, and neither tenant gains a row in `run`, `step_execution`, `envelope_payload` or `event`

### Requirement: The in-memory store obeys the database store's contract
`createMemoryRunStore()` SHALL answer every `RunStore` method as `createRunStore(pool)` does, with the same results and the same `RunDataError` codes.

#### Scenario: One operation sequence gives equal results in both stores
- **WHEN** one sequence runs on `createRunStore(db.appPool)` and on `createMemoryRunStore()`: `createRun` of `NEW_RUN("r_1")` as A, again with another input, as B, and with `mode` `dry`; `getRun` as A, as B and of `r_x`; `transition` to `running` from `["queued"]`, again, to `completed` from `["running"]` with `output` `{ verdict: "approve" }`, to `cancelled` from `["queued", "running"]`; `recordStep` of `STEP("r_1", "classify", 0)`, again with `state` `completed` and `seq` 9, node `route` with `seq` 0, a step of `r_x`; `listSteps` with `{ limit: 1 }` and `{ limit: 1, afterSeq: 0 }`; `getPayload` of the input digest, the output digest, an unstored digest, A's digest as B, and `"xyz"`
- **THEN** each call's value, or the `code` of its `RunDataError`, deep-equals between the stores; explicitly the second `createRun` returns the first record, the `dry` call and `route` reject with `RUN_DATA_INVALID`, the repeated `running` and the `cancelled` transition return `null`, the second `recordStep` keeps `seq` 0, and A's final `getRun("r_1")` has `state: "completed"`

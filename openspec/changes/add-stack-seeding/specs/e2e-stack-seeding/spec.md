## Purpose

What the pytest journeys need on the stack profile: a control server, a one-page sign-in, the seed of a reset database, the conftest and a run step.

## ADDED Requirements

### Requirement: The stack control server answers the fake's control API on loopback only
`startStackControl(opts)` SHALL listen on `127.0.0.1` at `opts.port` (default `STACK_CONTROL_PORT`) and answer: `POST /reset` by running `opts.reset()` one call at a time with 204, or, when that rejects, 500 `STACK_RESET_FAILED`, the message `The stack reset failed at step <step>` and `details.step` the rejection's `step` when that is 1 to 64 characters of letters, digits, spaces and `. _ : / -` starting with a letter or digit, else `unknown`; `GET /seed` with 200 `{ users }`, each user of `opts.users()` cut to `username`, `password`, `displayName`, `tenantName` and `capabilities` (500 `STACK_SEED_FAILED` when `opts.users()` throws); everything else, `POST /faults` and `DELETE /faults` included, with 404 `NOT_FOUND`. It SHALL write nothing to stdout or stderr, and `close()` SHALL wait for a running reset.

#### Scenario: Reset, a serialised pair and a failing reset
- **WHEN** `startStackControl({ port: 0, reset, users })` runs with a `reset` that records `start<n>` and `end<n>` around a 30 ms wait; `POST /reset` is sent twice together; then four times where `reset` rejects: an `Error` `password=hunter2 failed` with `step` `health`, an `Error` `boom hunter2`, one with `step` `POST /api/v1/teams`, one with a `step` of 65 `s`; stdout and stderr are captured
- **THEN** the first two answer 204 and the record is `start1,end1,start2,end2`; the next four answer 500 with `{ "error": { "code": "STACK_RESET_FAILED", "message": "The stack reset failed at step health", "details": { "step": "health" } } }` and `step` `health`, `unknown`, `POST /api/v1/teams`, `unknown`; no body holds `hunter2`; nothing was written to stdout or stderr; `url` starts `http://127.0.0.1:`

#### Scenario: Seed users, other routes and close
- **WHEN** with `users` returning `alice` and `carol` as `OverlayUser` values, `GET /seed` is sent; then `POST /faults`, `DELETE /faults`, `GET /reset`, `GET /` and `PUT /seed`; then `GET /seed` with a `users` that throws; and `close()` while a reset waits on a gate that opens after the call
- **THEN** the seed answer is 200 with `cache-control` `no-store` and the body `{ users: { alice, carol } }`, each user with exactly the keys `username`, `password`, `displayName`, `tenantName`, `capabilities`; the five other requests answer 404 `{ "error": { "code": "NOT_FOUND", "message": "Not found" } }`; the throwing `users` answers 500 `STACK_SEED_FAILED`; `close()` resolves after the reset ended; a later connection is refused

### Requirement: The runner starts the control server only when given one
`runnerMain(argv, opts)` SHALL, when `opts.control` is given, start `startStackControl(opts.control)` after the forwarders and before the child, close it after the child ends in every case, and, when it cannot listen, close the forwarders, not start the child, write `runner: the stack control server could not start (<error code>)` and a newline to stderr and answer 1; without `opts.control` it SHALL start none. As the entry script it SHALL pass `stackControlOptions(process.env.STACK_DIR ?? "/run/stack-e2e")`.

#### Scenario: Control on, off and on a busy port
- **WHEN** `runnerMain` runs with `forwards: []` and a free `port`: with `control` `{ port, reset, users }` and a child fetching `http://127.0.0.1:<port>/seed` that exits 0 on a 200; without `control` and a child that exits 0 only when that fetch is refused; with `control` on a port another listener holds and a child that would write a marker file; and with the child `node -e process.exit(7)`
- **THEN** the answers are 0 (the port refused afterwards), 0, 1 with stderr `runner: the stack control server could not start (EADDRINUSE)` and no marker file, and 7; `runner-main.ts` holds `stackControlOptions(` and `process.env.STACK_DIR`

### Requirement: signInThroughKeycloak signs in through the provider's one-page form
`signInThroughKeycloak(opts)` SHALL `GET <engineOrigin>/auth/oidc/login?return_to=%2F`, follow the redirects by hand (at most 5 to the provider's page), find the `<form>` whose `id` is `kc-form-login` whatever the order of its attributes, post `username` and `password` to its `action` (resolved against the page, `&amp;` unescaped), follow the redirect to the engine's callback with cookies kept per origin, read `GET /api/v1/me` and answer `{ cookie, csrfToken, capabilities, request }`, `cookie` being the session cookie pair. `request(method, path, body?, headers?)` SHALL send the cookie, `accept: application/json`, `x-csrf-token` for every method but GET and a JSON body when given, answer `{ status, body }` for every status, and take the new `csrfToken` from a `GET /api/v1/me` it makes. A failure SHALL reject with `StackLoginError`, a fixed message with no page text or credential, and code `STACK_LOGIN_TWO_STEP` when the form has no input named `password`, else `STACK_LOGIN_FAILED`.

#### Scenario: A session from the fake OIDC on the in-process stack
- **WHEN** on `startE2eStack` with all its parts `signInThroughKeycloak` runs for `alice`, `bob`, `carol` and `mallory` with `fake.passwordOf(name)`; with `carol` `request("GET", "/api/v1/me")` twice, then `request("POST", "/api/v1/teams", { teamId: "t-probe" })` and `request("GET", "/api/v1/nope")`; then for `carol` with password `wrong`, for `nobody`, and with `engineOrigin` `http://127.0.0.1:1`
- **THEN** each `cookie` matches `^ursitoare_session=[A-Za-z0-9_-]+$` and each `csrfToken` is 43 characters of `[A-Za-z0-9_-]`; `capabilities` hold `test_flow` for `alice` and `mallory`, `read_registry` for `bob`, `manage_users_roles` for `carol`; after the two `me` calls `csrfToken` equals the second answer's token, the POST answers `{ status: 201, body: { teamId: "t-probe" } }` and the last request 404 `NOT_FOUND`; the three failures reject `STACK_LOGIN_FAILED`: `the provider refused the credentials` twice, `sign-in step login could not be sent`

#### Scenario: A Keycloak-shaped form, a two-page form and the refusals
- **WHEN** `signInThroughKeycloak` runs against an engine and a provider server (two origins) on rows F1 to F7 of `test-plan-rows.md` § Sign-in forms (Keycloak's attribute order and cookies; the fake's order; a username-only form; no form; a foreign redirect; a refusing callback; a bad password)
- **THEN** F1 and F2 answer the session `ursitoare_session=S1`, `CSRF1`, and `request("POST", "/api/v1/teams", { teamId: "finance" })` reaches the engine with `x-csrf-token` `CSRF1`, `content-type` `application/json` and that cookie; F3 rejects `STACK_LOGIN_TWO_STEP`, F4 to F7 `STACK_LOGIN_FAILED`, each with its row's message

### Requirement: seedPlan lists the seed in order and holds no secret
`seedPlan(seed, issuer)` SHALL answer, in order, for each tenant `tenant-create --name <name>` then `tenant-idp --tenant-name <name> --issuer <issuer> --organization <organization>`; `tenant-sink --tenant-name <name>` for each tenant with `sink`; `admin bootstrap-admin --tenant { tenantIdOf: <name> } --issuer <issuer> --operator stack-seed` for each with `bootstrapAdmin`; one `catalogue` step for the first tenant; one `groupmap` step per `seed.tenantMaps`; then as `carol` `POST /api/v1/teams`, one `PUT /api/v1/idp-group-map` per `seed.groupMaps` (`roleId` or `teamId` only when not null), `POST /api/v1/tool-servers` and `POST /api/v1/credentials`. `STACK_SEED` SHALL name `E2E tenant` (`org-a`, sink, bootstrap admin), `Tenant B` (`org-b`), the team `finance`, the three `RBAC_SEED_MAPPINGS`, one map of `Tenant B` and the server `acme`.

#### Scenario: The seed plan in order
- **WHEN** `seedPlan(STACK_SEED, "http://localhost:8180/realms/ursitoare")` runs twice, and `seedPlan({ ...STACK_SEED, tenants: [], tenantMaps: [] }, "i")` once
- **THEN** the full plans deep-equal the 14 steps of `test-plan-rows.md` § Seed plan, the `surface` equal to `fixtureSurface(["erp.lookup_vendor@1", "erp.create_payment@1"], { untrustedResult: { "erp.lookup_vendor@1": false, "erp.create_payment@1": false } })` and the last body `{ toolServerId: "acme", authScheme: "API_KEY_HEADER", headerName: "x-fake-tools-key", value: "stack-seed-key" }`; only the sixth holds a `tenantIdOf`; the reduced plan holds six `api` steps and no `cli`

### Requirement: seedStack seeds through the owner commands, the owner pool and the API
`seedStack(deps)` SHALL run `seedPlan(STACK_SEED, deps.issuer)` in order: `cli` steps through `runCli` with `deps.ownerEnv` and `createDefaultRegistry()`, each `{ tenantIdOf }` taken from the second field of that tenant's `tenant <id> "<name>" …` line; `catalogue` through `importCatalogue` and `groupmap` through `setGroupMapping`, with a pool from `URSITOARE_DATABASE_OWNER_URL` and the password file `URSITOARE_DATABASE_OWNER_PASSWORD_FILE` names, read when the call starts; before the first `api` step one sign-in of `deps.users.carol` and a check that she holds her `capabilities`; then each `api` step through that session, a 409 counting as present. It SHALL resolve `{ steps }`, writing nothing to stdout or stderr. A failure SHALL reject with `SeedError`, message `seed failed at step <step> (<reason>)`: `step` a command name, `catalogue`, `groupmap`, `<METHOD> <path>`, `owner password`, `sign-in carol` or `roles carol`; `reason` a CLI error code, `unreadable`, `no_user`, a `StackLoginError` code, `missing_<capability>` or `http_<status>`.

#### Scenario: A fresh seed, a repeat and two other tenants
- **WHEN** on `startE2eStack` without its `tenant-b`, `rbac`, `catalogue` and `tool-servers` parts, with `Other X` and `Other Y` inserted, `seedStack` runs twice with the fixtures of `test-plan.md` (`fetch` records every `/api/` call); then each user signs in
- **THEN** both runs resolve `{ steps: 14 }` with nothing written to stdout or stderr; the recorded calls are `GET /api/v1/me 200`, `POST /api/v1/teams 201`, three `PUT /api/v1/idp-group-map 200`, `POST /api/v1/tool-servers 201`, `POST /api/v1/credentials 201`, and in the second run `409` for the three POSTs; the tenants, their rows and the two sink routes are those of `test-plan-rows.md` § Seed result (20 blocks and four mappings for `E2E tenant`, one mapping for `Tenant B`, nothing for the others); every user's `/api/v1/me` grants the `capabilities` of `OVERLAY_USERS`

#### Scenario: Each failing step names itself

### Requirement: The seed settings come from the state directory and match the compose file
`stackSeedDeps(dir)` SHALL answer `ownerEnv` with the six variables of `test-plan-rows.md` § Settings, each the `owner-job` value of the compose file with `/run/secrets/` replaced by `<dir>/secrets/`; `engineOrigin` `http://127.0.0.1:8080`; `issuer` `STACK_ISSUER`; `users` from `readUsers(dir)`; it SHALL read no secret file. `stackControlOptions(dir, hooks?)` SHALL answer a `reset` that builds `stackResetDeps(dir)` and `stackSeedDeps(dir)` when called (a failure of either rejects `SeedError` `settings` `unreadable` before any hook), runs the reset hook (default `resetEngineDatabase`), then the seed hook (default `seedStack`), a rejection of the first ending the call, and a `users` that reads `readUsers(dir)` at each call.

#### Scenario: Settings from files and the control composition
- **WHEN** `stackSeedDeps` runs on a temp `dir` holding only `users.json`; `stackControlOptions(dir, hooks)` runs with recording hooks, `secrets/db_superuser_password` `SUPER-fixture` and `secrets/db_owner_password` `OWNER-fixture`, and `reset()` is called; then with a reset hook rejecting `{ step: "create" }`; then on a `dir` without `secrets/`; then `users()` before and after `users.json` is rewritten; and `deploy/compose.yaml` and `deploy/compose.e2e.yaml` are read
- **THEN** `ownerEnv` is the table of `test-plan-rows.md` § Settings (each name in `SECRET_FILES`); `engineOrigin` equals the engine's `URSITOARE_PUBLIC_BASE_URL` and the runner's `E2E_BASE_URL`, `issuer` the engine's `URSITOARE_OIDC_ISSUER` (`${VAR:-default}` resolved) and the port of the runner's `E2E_STACK_CONTROL_URL` is `STACK_CONTROL_PORT`; the hooks ran reset (with `stackResetDeps(dir)`) then seed (with `stackSeedDeps(dir)`); the failing reset ended the call and the seed hook did not run; the missing `secrets/` rejected `seed failed at step settings (unreadable)` before any hook; `users()` answered the old, then the new file; no message holds `SUPER-fixture` or `OWNER-fixture`

### Requirement: The conftest uses the stack control server, marks the fake-only tests and checks the roles after sign-in
`e2e/conftest.py` SHALL give `seed_users(e2e_profile)` (the `users` fixture's body): on the stack profile with `E2E_STACK_CONTROL_URL` set it reads `GET /seed` there, as the fake profile reads `E2E_CONTROL_URL`, else raises as before. At import it SHALL set `L4_E2E_BASE_URL` from `E2E_BASE_URL` when only the latter is set (the generated `test_l4_c_*.py` files read it at import). It SHALL define `FAKE_ONLY_TESTS`, `is_fake_only(file_name, test_name)`, a `pytest_configure` that registers the marker `fake_only` and a `pytest_collection_modifyitems` that adds it by `originalname`. `login`, for a user dict with `capabilities`, SHALL take the `GET /api/v1/me` answer the page itself fetches (`is_me_response`) and call `check_capabilities(user, granted)`, which fails naming each missing capability; it SHALL make no request of its own to `/api/v1/me` (each answer ends the page's CSRF token).

#### Scenario: users on the stack profile and the login check

- **WHEN** `is_fake_only` runs on five pairs, `pytest_collection_modifyitems` on two stub items (the Alice journey named `<test>[chromium]` with `originalname` `<test>`, and `test_m7_tools.py::test_x`), `pytest_configure` on a recording config, and pytest itself collects `e2e` with `-m fake_only` and with `-m "not fake_only and not stack"`, as a child with only `E2E_BASE_URL` set

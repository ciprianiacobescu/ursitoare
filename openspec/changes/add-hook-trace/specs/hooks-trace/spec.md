## Purpose

A node attempt that ran hooks leaves their trace on its step row, the steps route serves it, and a pure function lists the approvals on a path for the policy check that arrives in M6.

## ADDED Requirements

### Requirement: The final row of a node attempt carries that attempt's hook trace
`visitNode` SHALL write `hooks` on the final row (completed, skipped or failed) of an attempt that ran at least one hook, as `{ inputOriginal, entries }`: `entries` are that attempt's `HookRun.entry` values in execution order, fused and own-step alike, and `inputOriginal` is the attempt's base input (the input of its `started` row) when an entry has `mutated: "input"`, else `null`; the `started` row, a row of an attempt without hooks and every row of a hookless run SHALL carry no `hooks`.

#### Scenario: Onion, mutate, retry and failure rows
- **WHEN** with the setup of test-plan.md § Rows, where `E(label, over)` is the entry `{ label, kind: "code", fused: true, attempt: 1, state: "completed", action: "continue", mutated: null, to: null, error: null, tool: null, idemKey: null }` with `over` applied, `onion`, `mutate`, `f-ret` and `bad-upper` each run to the end through `executeRun` on the memory store with a recording `hookObserver`, and `listSteps` is read after each; then the hookless `pay-once` run of `add-interpreter-core` runs

### Requirement: A replay rewrites the same trace
A replay over a prefix of the recorded step values SHALL leave every row equal to the first run's, `hooks` included: a row written after a partly replayed attempt SHALL carry the entries of the replayed steps (fused records and recorded own-step values) and of the fresh ones, and a fully replayed run SHALL write nothing.

#### Scenario: Replay of onion-own keeps the trace

- **THEN** after each replay `listSteps` deep-equals the first run's four rows; the `pay` row holds `hooks` with the six entries of `onion` in the same order, the sixth (`post:rule.rule_a`) with `fused: false`, the other five with `fused: true`, and `inputOriginalRef` `null`, for `k` 4 (`pay` and all its steps run again) and for `k` 6 (the fused records of `pay` and `pay#done` are replayed and the own step runs again); for `k` 9 no step runs; each time the new observer receives the first run's eight entries in order, replayed ones included (add-hook-runtime design 1.8)

### Requirement: The steps route serves the trace and never the original input
`GET /api/v1/runs/{runId}/steps` SHALL answer each stored `hooks` in full in its `StepView` and no `hooks` key for a row without one, and `GET /api/v1/runs/{runId}/payloads/{sha256}` SHALL keep serving only the digests that a run row references, so the `inputOriginalRef` of a trace answers 404 `NOT_FOUND`; `docs/api/openapi.json` SHALL equal the served document.

### Requirement: approvalsOnPath lists the approvals on a path
`approvalsOnPath(steps)` SHALL return, in input order, `{ nodeId, decision, approver }` for each step whose `kind` is `human.approval`, whose `state` is `completed` and whose `outcome` is `approved` or `rejected` (`decision` is the outcome), with `approver` the string `output.approver` when `output` is an object with that own member, non-empty and of at most 128 characters, else `null`; any other step, a `timeout` outcome included, SHALL give nothing, a step repeated in the path SHALL appear each time, and a non-array argument or a non-object entry SHALL give nothing and not throw.

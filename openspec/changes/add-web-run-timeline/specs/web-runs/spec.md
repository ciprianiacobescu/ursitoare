## Purpose

The run pages let a signed-in user list runs, follow one run on a timeline of its steps with their inputs and outputs, and start a mocked test run from the flow editor; the closing journey of M4 proves it in a browser.

## ADDED Requirements

### Requirement: Run views are parsed strictly and read through four loaders
The web app SHALL parse the `RunView`, `StepView` and `PayloadView` of the runs API, rejecting any answer that does not fit, and read the run list, a run, its steps and a payload through `runListFetcher`, `loadRun`, `loadSteps` and `loadPayload`; a failing list SHALL leave the kit table's retry button "Try again".

#### Scenario: Views are parsed strictly
- **WHEN** `parseRunView(RUN)`, `parseStepView(STEPS[2])` and `parsePayloadView({ sha256: D("4"), mediaType: "application/json", size: 38, data: { payment_id: "P-1" } })` run; `parseRunView` gets `RUN` with `state: "paused"`, no `ownerTeam`, `principal.kind: "robot"`, `error: { code: "X" }`, a 63-character `inputRef`; `parseStepView` gets `STEPS[2]` with `seq: -1`, `taint: [1]` and `state: "done"`; `parsePayloadView` gets `size: -1` and no `data`; `parseRunView` gets `RUN` plus `extra: 1`
- **THEN** the valid inputs give values deep-equal to them, `principal`, `error` and `taint` being copies; every invalid input gives `null`; `extra: 1` is dropped

#### Scenario: Loaders call exactly the run routes
- **WHEN** a recording client serves `runListFetcher(client)` called with `{ cursor: null, limit: 50, signal }` then `{ cursor: "c1", limit: 50, signal }`, answered `{ items: [RUN], next_cursor: "c1" }` then `{ items: [{ ...RUN, state: "paused" }], next_cursor: null }`; `loadRun(client, "run_1", signal)` and of `"bad id"`; `loadSteps(client, "run_1", signal)` answered `{ items: [STEPS[0], STEPS[1]], next_cursor: "c1" }` then `{ items: [STEPS[2], STEPS[3]], next_cursor: null }`, and a `loadSteps` whose client answers a new cursor forever; `loadPayload(client, "run_1", D("3"), signal)` (the input of `pay`), `loadPayload(client, "run_1", D("4"), signal)` and of a short digest; the kit's `createCursorList(runListFetcher(client))` loads against a client whose `get` rejects `ApiRequestError(500, "INTERNAL", "m")`, then `retry()` against it now answering `{ items: [RUN], next_cursor: null }`, `tableView` read after each
- **THEN** the list calls are `{ path: "/runs", opts: { query: { limit: 50 }, signal } }` then the same with `cursor: "c1"` in the query; the first page is `{ items: [RUN], next_cursor: "c1" }`, the second rejects with `ApiRequestError` of status 200, code `INVALID_RESPONSE`; `loadRun` makes exactly `{ path: "/runs/run_1", opts: { signal } }` and returns `RUN`; the step and payload calls are those of reference.md § Calls, giving `{ steps: STEPS, truncated: false }`, the endless one called 5 times with `truncated: true`, and the parsed views of the input and output payloads (reference.md § Calls); the bad id and digest reject with `RangeError` without a call; after the failure `tableView` gives `retry` `again`, `retryLabel` `Try again`, `showError` true; after the retry the state is `loaded` with `[RUN]` and `retryLabel` is null

### Requirement: Step renderers are registered by node kind
`registerStepRenderer` SHALL add a renderer for one node kind, and `stepRendererFor` SHALL return it, or a default renderer for a kind nobody registered, with `stepRenderers.list()` holding the built-ins `block`, `switch`, `wait` and `end` first.

#### Scenario: Built-ins, a default, registration and refusals
- **WHEN** `stepRenderers.list()` is read; `stepRendererFor` gets `"block"`, `"switch"`, `"wait"`, `"end"`, `"mystery"` and `"__proto__"`; `registerStepRenderer` gets `{ kind: "llm.extract", label, details }` and the lookup and list are read again; then it gets `llm.extract` and `block` again and the seven `BAD_RENDERERS` (reference.md § Fixtures)
- **THEN** the first list has the kinds `["block", "switch", "wait", "end"]` and each lookup returns the object in the list; the other two kinds give one default renderer, `kind` `"*"`, whose `label(STEP(0, "x", "mystery"))` is `"mystery (unknown kind)"` and `details` gives `[]`; after the registration the lookup returns the registered object and the kinds end with `"llm.extract"`; the two repeats throw `StepRendererError` with `code` `STEP_RENDERER_DUPLICATE`, the seven bad ones `STEP_RENDERER_INVALID`; each refusal leaves the list unchanged

### Requirement: The timeline shows every step with its state, details and payload
`stepStateLabel`, `timelineItems` and `stepDetailRows` SHALL list a run's steps in `seq` order, label a `started` step of a terminal run (whatever its state) "Interrupted" with the note "Not finalized" and never running, show a mocked `wait` with outcome `skipped`, and link a decision only when `policyDecisionId` is set; `payloadShown` SHALL show a payload only as the text of what was loaded, and `setPayloadLoad` SHALL confine a payload failure to its own digest.

#### Scenario: Items, states, details and payloads
- **WHEN** `stepStateLabel` gets each of the four step states with each of the five run states; `timelineItems` gets `[STEPS[2], STEPS[0], STEPS[3], STEPS[1]]` with `"completed"`; `[STEP(0, "lookup", "block", { state: "started", endedAt: null })]` with `"running"`, `"failed"`, `"cancelled"`, `"completed"`; and `[STEP(1, "nap", "wait", { outcome: "skipped" })]` with `"completed"`; `stepDetailRows` gets `STEPS[2]` with `"completed"`, the started step with `"completed"` and `STEP(2, "pay", "block", { state: "failed", error: { code: "E_X", message: "failed", node: "pay" }, policyDecisionId: "dec_1" })` with `"failed"`; `decisionHref` gets `"dec_1"` and `"a b"`; `runErrorText` gets `{ code: "E_X", message: "failed", node: null }`, `{ code: "E_X", message: "failed", node: "pay" }` and `null`; `payloadShown` gets `(null, undefined)`, `(D("4"), { phase: "ready", value: { payment_id: "P-1" } })`, and `(D("4"), { phase: "error", error: new ApiRequestError(404, "NOT_FOUND", "m") })`; `setPayloadLoad(LOADS, D("4"), { phase: "error", error: new ApiRequestError(404, "NOT_FOUND", "m") })` where `LOADS` maps `D("3")` to `{ phase: "ready", value: { vendor_id: "V-1" } }` and `D("4")` to `{ phase: "loading" }`
- **THEN** the first items are `{ seq, nodeId, text }` for `lookup`, `route`, `pay`, `done` (seq 0 to 3) with the texts `"block · completed"`, `"switch: active · completed"`, `"block · completed"`, `"end · completed"`; `stepStateLabel` gives `{ label: "Interrupted", note: "Not finalized" }` for `started` with `completed`, `failed`, `cancelled`, `{ label: "running", note: null }` for `started` with `queued`, `running`, and `{ label: <the state>, note: null }` for the other 15 pairs; the started step reads `"block · running"` for `"running"` and `"block · Interrupted (Not finalized)"` for the other three; `nap` reads `"wait: skipped · completed"`; the rows for `STEPS[2]` are `PAY_ROWS` (reference.md § Fixtures); the failed `pay` step's rows end as `PAY_FAILED_TAIL` (reference.md § Fixtures); the started step's State row is `Interrupted (Not finalized)`; `decisionHref("a b")` is `null`; `runErrorText` gives `"E_X: failed"`, `"E_X: failed (at pay)"` and `null`; `payloadShown` gives `"none"`, `{\n  "payment_id": "P-1"\n}`, and `"That item does not exist, or you cannot see it."`; `setPayloadLoad` returns a new Map with the same ready object for `D("3")` and the error load for `D("4")`, `LOADS` unchanged, and `payloadShown` of the two gives `{\n  "vendor_id": "V-1"\n}` and the NOT_FOUND text (plain text in that block, no alert)

### Requirement: Polling follows a run until it ends
`nextPollDelay` SHALL give the wait before the next look at a run (250 ms doubling to 2,000 ms, none once terminal), and `followRun` SHALL reload the run and its steps after each wait until the run is terminal, passing every snapshot to `onUpdate`, within a deadline; a failed poll SHALL show the `ErrorPanel` and the button "Try again", keep the earlier snapshot, stop polling and restart only on that button, and a malformed run id (a `RangeError`) SHALL show the 404 panel "Not found" without a request.

#### Scenario: Delays, a followed run, a deadline and failures
- **WHEN** `nextPollDelay` gets `("queued", 0)`, `("running", n)` for n = 0, 1, 2, 3, -1, NaN, and `("completed", 0)`, `("failed", 7)`, `("cancelled", 0)`; `followRun(client, "run_1", { sleep, now, deadlineMs: 20000, onUpdate })` runs against a client that answers `/runs/run_1` with `queued`, `running`, `running`, `completed` in turn and `/runs/run_1/steps` with 0, 1, 2 and 4 steps, a `sleep` that records its delay and resolves, and `now` returning 0; then against a client that always answers `running` with `now` returning 0, 6000, 12000, 18000, 24000 in turn; `followRun`, `loadRun(client, "bad id!")`, `failureView` and `runPageView` run on the six failure cases of reference.md § Failures (a rejecting poll then a restart, a 403 run, an aborted signal, a malformed answer, a malformed route id, the page views)
- **THEN** the delays are 250, 250, 500, 1000, 2000, 250, 250 and `null` three times; the first follow resolves with the last snapshot (`completed`, the 4 steps), `sleep` got `[250, 500, 1000]`, `onUpdate` got the four states in order, and the client was asked `/runs/run_1` and `/runs/run_1/steps` alternately, four times each; the second rejects with `RunFollowError` of `code` `RUN_FOLLOW_TIMEOUT`, `sleep` having got `[250, 500, 1000]`; each failure case has the outcome of reference.md § Failures, strictly equal

The feature files `80-runs.tsx` and `81-run.tsx` SHALL register the pages `/runs` (navigation entry "Runs", capability `read_run`) and `/runs/:runId` and, from `80-runs.tsx`, the editor panel "Test run", with the names of `pages.ts`, using kit tokens only.

### Requirement: The Test run panel starts a mocked run
The editor panel "Test run" SHALL show its form only for a saved version that is not a `draft` and a session with the capability `test_flow`, parse both texts as JSON objects before any request, and start the run with `startTestRun`, explaining a refusal with `testRunFormErrors`.

#### Scenario: What the panel shows and what its inputs must be
- **WHEN** `testPanelView(session, version)` gets `null, null`; `{ status: "signed_out" }` and `{ status: "failed", code: "INTERNAL" }` with `null`; a ready session without `test_flow` and a `validated` version; a ready session with `test_flow` and `null`, then with `V` in each of the six version states; `parseTestInputs` gets `("{}", "{}")`, `(INPUT_TEXT, MOCKS_TEXT)`, `("", "{}")`, `("[1]", "{}")`, `("{", "null")` and `('{"__proto__":{"x":1}}', "{}")`
- **THEN** the views are `{ kind: "loading" }`; `unavailable` twice, `denied`, `no_version` for `null` and `draft` (texts: reference.md), and `{ kind: "form", number: 2, hash: V.hash }` for the other five states; the inputs give the six results of reference.md § Pages (`ok` true with the parsed objects for the first, second and last, which has an own property `__proto__` in `input`; `errors` for the other three)

#### Scenario: Starting a run and explaining a refusal
- **WHEN** a recording client answers `startTestRun(client, { flowId: "demo-pay", hash: "sha256:" + D("a"), input: INPUT, mocks: MOCKS }, "key-1")` with `{ run: RUN_QUEUED }`, then with `{ run: { ...RUN_QUEUED, state: "paused" } }`; `startTestRun` gets the flow id `"Bad_Id"` (underscore, upper case: outside the flow-id grammar of reference.md § Calls) and, separately, the hash `"sha256:xyz"`; `registerRunMessages()` runs twice; `testRunFormErrors` gets each `ApiRequestError` (and `new Error("boom")`) of the table in reference.md § Messages
- **THEN** the call is exactly `{ path: "/flows/demo-pay/versions/sha256%3A" + D("a") + "/test", body: { input: INPUT, mocks: MOCKS }, opts: { headers: { "Idempotency-Key": "key-1" } } }` and the result equals `RUN_QUEUED`; the second answer rejects with `ApiRequestError` of status 200, code `INVALID_RESPONSE`; `"Bad_Id"` and `"sha256:xyz"` each reject with `RangeError` and no POST is made; the registration does not throw; `testRunFormErrors` gives the right-hand value of each row of that table, strictly equal

### Requirement: The run logic works against the real engine
The logic functions SHALL start, follow and read a mocked run on the e2e stack's engine: a team reader reads but cannot start one, another tenant sees nothing.

#### Scenario: Alice, bob and mallory use the engine
- **WHEN** `m4-runs.test.ts` starts the stack (asserting `stack.handles.has("durable")`) and signs in alice, bob and mallory; alice creates `demo-pay` for `finance`, saves `DEMO_PAY`, validates it, starts a test run with `INPUT` and `MOCKS` and follows it (`followRun`); `loadPayload` reads the `inputRef` and `outputRef` of its `pay` step; alice and bob read the list (`runListFetcher`), bob the run and its steps; bob calls `startTestRun`; mallory calls `loadRun` and the list; alice calls `startTestRun` with `mocks: {}`; the `/me` capabilities of alice and bob are read
- **THEN** the start answer is a `RunView` of `demo-pay` with `mode` `mock`, `ownerTeam` `finance` and alice's id as `principal.userId`; the followed run is `completed` with `terminalNode` `done`; its steps are `lookup`, `route`, `pay`, `done` (kinds `block`, `switch`, `block`, `end`, all `completed`), `route` has the outcome `active`, and the `pay` input is `PAY_INPUT` and its output `{ payment_id: "P-1", status: "created" }`; both lists hold the run id and bob reads the same run; bob's start rejects with status 403; mallory's `loadRun` rejects with status 404 and her list is empty; alice's start with `{}` rejects with status 422, code `TEST_MOCK_MISSING`, and `testRunFormErrors` of it (after `registerRunMessages()`) is `{ mocks: MISSING + " Missing: lookup, pay." }`; both capability sets hold `read_run`, alice's holds `test_flow` and bob's does not

`e2e/test_m4_runs.py` SHALL show an author test-running a flow and following the run on the timeline, and a team reader opening it without a way to start one, with `assert_accessible(page)` on every page.

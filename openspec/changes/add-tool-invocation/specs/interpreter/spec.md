## ADDED Requirements

### Requirement: An invoker that authorizes is asked before the intent and its decision rides the step value
When `services.invoker.authorize` exists, `blockRuntime` SHALL call it inside the node's first step, after `prepare()` and before `effects.before`, with `{ ...ctx, taint: services.inputTaint?.() ?? ctx.taint }`, call `invoke` with `authorization` set to its answer, return the step value `{ output, decisionId }` (read) or `{ output, idemKey, decisionId }` (effect), and call `services.decided?.(decisionId)` after the step returned, fresh or replayed; a throw of `authorize` SHALL end the step before `effects.before` and `invoke`. Without `authorize` the calls, contexts and step values SHALL be exactly M5's and `decided` SHALL not be called. `INTERPRETER_TOOL_DENIED` SHALL be in `InterpreterErrorCode` and in the list that survives a replay.

#### Scenario: Order, values, denial, replay and the unchanged M5 path
- **WHEN** `blockRuntime.execute` runs over `memoryWorkflowOps`, a gate answering `invoke` with `ik_pay_1` and an invoker with `authorize` answering `{ decisionId: "dec_1", permit: P }` for `pay` (`inputTaint` `() => ["extracted"]`) and `dec_2` for `lookup` (no `inputTaint`, no `ctx.taint`); then `authorize` rejects with `INTERPRETER_TOOL_DENIED` `{ reason: "policy", decisionId: "dec_3" }`; then `pay` replays over its recorded values; then an invoker without `authorize` runs both nodes
- **THEN** `pay` records `authorize`, `before`, `invoke`, `after` in steps `pay` and `pay#done`; `authorize` got `{ ...CTX("pay"), taint: ["extracted"] }`, `invoke` got `{ ...CTX("pay"), idemKey: "ik_pay_1", authorization: { decisionId: "dec_1", permit: P } }`, the first value is `{ output: PAID, idemKey: "ik_pay_1", decisionId: "dec_1" }` and `decided` got `"dec_1"` once; `lookup`'s value is `{ output: LOOKUP_OK, decisionId: "dec_2" }` with `taint` undefined in its `authorize` ctx; the denial rejects with that error, with only `authorize` called (no `before`, `invoke`, `decided`); the replay calls nothing and `decided` gets `"dec_1"`; the invoker without `authorize` gets contexts with no `authorization`, `taint` or `approvals` member, records `LOOKUP_OK` and `{ output: PAID, idemKey: "ik_pay_1" }`, and `decided` is never called; `toInterpreterError` of an object with code `INTERPRETER_TOOL_DENIED` is an `InterpreterError`

### Requirement: A block hook is authorised as a hook call and a denial is never continued
`blockHookRunner` SHALL, when `services.invoker.authorize` exists, call it in the hook's first step after its arguments are checked and before `effects.before` (before the invoker for a `read` hook) with `{ ...step, attempt: hctx.attempt, hook: { phase, label }, taint: services.argsTaint?.(placement.hook.with) ?? ["untrusted"] }`, pass the answer to `invoke`, and leave U43's `HookRun` step value unchanged. An `INTERPRETER_TOOL_DENIED` from `authorize` SHALL fail the node whatever `on_error` says; any other failure of `authorize` SHALL be `HOOK_ERROR` with reason `tool_failed`. `pipeline.ts` SHALL give every hook `argsTaint` = `valueTaint` of the value over that hook's `HookTaintScope`.

#### Scenario: Taint of a hook's arguments, the default and the denial
- **WHEN** `blockHookRunner.run` runs for `notify` (`slack.post_message@1`, send, slot 1, attempt 1) over a recording invoker with `authorize` and gate: with no `argsTaint`; with `argsTaint` answering `["extracted"]`; with `authorize` rejecting `INTERPRETER_TOOL_DENIED` under `on_error` `fail` and `continue`; with `authorize` rejecting `Error("db down")` under both; and with an invoker without `authorize`
- **THEN** the calls are `authorize`, `before`, `invoke`, `after`; `authorize` got `hook: { phase: "post", label: "notify" }`, `attempt: 1` and `taint` `["untrusted"]` (first run) or `["extracted"]` (second), `argsTaint` was called once with the hook's `with` object, the step value is U43's `HookRun` without `decisionId`; both denials reject with `INTERPRETER_TOOL_DENIED` and call neither `before` nor `invoke` nor `after`; `db down` rejects `HOOK_ERROR` `{ hook: "pay:post:notify", reason: "tool_failed" }` under `fail` and is a failed entry under `continue`; the invoker without `authorize` records U43's calls and contexts exactly

### Requirement: Rows carry the decision and a denied attempt keeps its decision id
`visitNode` SHALL give `NodeServices.inputTaint` (the effective input taint of the attempt so far, the labels its final row would carry) and `decided`, write `policyDecisionId` on the attempt's final row from `decided` (the `started` row and an attempt without a node authorization carry `null`), and, when nothing was `decided` for the attempt, use the `details.decisionId` of its error unless the error has `details.hook` (a denied node call); a hook's decision SHALL not be passed to `decided` and never becomes the row's id. A replay over recorded step values SHALL write the same ids; a mock run SHALL write `null`.

#### Scenario: Fresh, replayed, denied and mock rows
- **WHEN** `read-then-pay` (`invokeRunVersion`, mode `live`, run `r_1`) runs through `executeRun` on the memory store with an invoker whose `authorize` answers `dec_<node>`; again over `memoryWorkflowOps("r_1", V)` for the seven recorded values and for the first four; with `authorize` rejecting at `pay` with `{ reason: "policy", decisionId: "dec_deny" }` and with `{ reason: "tool_unbound" }`; and in mode `mock` with `createMockInvoker({ lookup: [{ output: LOOKUP_OK }], pay: [{ output: PAID }] })`
- **THEN** the final rows of `lookup`, `pay` and `done` have `policyDecisionId` `dec_lookup`, `dec_pay` and `null`, every `started` write has `null`, both replays leave the same rows, the `policy` run ends `failed` with error `{ code: "INTERPRETER_TOOL_DENIED", message: 'tool call of "pay" is not permitted (policy)', node: "pay", details: { reason: "policy", decisionId: "dec_deny" } }` and a `pay` row `failed` with `dec_deny`, the `tool_unbound` run's `pay` row has `null`, and the mock run's `executed` list is `["run:load", "run:start", "lookup", "pay", "pay#done", "done", "run:finish"]`, its `lookup` and `pay` step values are `LOOKUP_OK` and `{ output: PAID, idemKey: "ik_pay_1" }` (the gate answers `ik_pay_1`) and every `policyDecisionId` is `null`

### Requirement: executeRun hands the approvals of the visited path to every call
`executeRun` SHALL keep the nodes it has visited as `PathStep`s (`nodeId`, `kind`, `state` `completed`, `outcome`, `output`), pass `approvalsOnPath` of the path so far as `approvals` of each visit, and `visitNode` SHALL put it on `StepContext.approvals` of every node call and hook call; with no `human.approval` visit it SHALL be `[]`.

#### Scenario: A path through an approval node
- **WHEN** `executeRun` runs the flow `lookup -> approval -> pay -> done` of `test-plan-runs.md` § Interpreter rows (the `approval` node of kind `human.approval` served by a stub runtime answering outcome `approved`, output `{ approver: "bob" }`), then the same with outcome `rejected`, each with a recording invoker that has `authorize`
- **THEN** the `authorize` contexts show `approvals` `[]` at `lookup` and at `pay` `[{ nodeId: "approval", decision: "approved", approver: "bob" }]` and `[{ nodeId: "approval", decision: "rejected", approver: "bob" }]`

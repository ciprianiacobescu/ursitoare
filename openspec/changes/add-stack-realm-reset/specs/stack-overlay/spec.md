### Requirement: planOverlay answers only what is missing, in creation order
`planOverlay(state, overlay)` SHALL answer, in this order: `POST /admin/realms/ursitoare/groups` `{ name }` for each overlay group the state lacks; `POST .../organizations` `{ name: alias, alias, enabled: true, domains: [] }` for each missing alias; `POST .../clients` for each missing client; `POST .../users` for each missing username (its `groups` the paths `/<name>`); `PUT .../users/<user id>/groups/<group id>` with body `null` for each group an existing user lacks; and `POST .../organizations/<organization id>/members` with the user id as body for each existing overlay user not yet in its existing organization. It SHALL answer `[]` when the state holds the overlay, delete and change nothing, address only those four collections, and throw `Error` `group <name> is neither in the realm nor in the overlay` for a group of an overlay user that neither holds. `overlayGaps(state, overlay)` SHALL answer one text per missing item (`group <name>`, `organization <alias>`, `client <id>`, `user <name>`, `user <name> in group <group>`, `user <name> in organization <alias>`), `[]` when none.

### Requirement: applyRealmOverlay reads the realm, writes in rounds and checks the result
`readAdminState(deps)` SHALL fetch a token (`POST <adminBaseUrl>/realms/master/protocol/openid-connect/token`, form `grant_type=password&client_id=admin-cli&username=<adminUser>&password=<adminPassword>`) and read with `authorization: Bearer <access_token>` the groups, each organization's members, the users with their groups and the clients (paths in `test-plan-data.md`). `applyRealmOverlay(deps, overlay)` SHALL repeat at most `MAX_OVERLAY_ROUNDS` (3) rounds of a new token, a read and, when `overlayGaps` is not `[]`, the requests of `planOverlay` in order; it SHALL answer `{ applied }` (one per 2xx write; a 409 on a POST counts as present, not applied) once a read shows no gap, and otherwise throw `Error` `overlay: the realm still lacks <gaps joined by ", ">`. A failing step SHALL throw `Error` `overlay: <step> <what>`: `<step>` is `the admin token request` or `<METHOD> <path>`, `<what>` is `answered <status>`, `answered no access token`, `answered a body that is not a list`, `timed out` (after `requestTimeoutMs`, default 30000) or `could not be sent`; no text holds a password, secret or response body.

### Requirement: prepareTemplate keeps the template current with the code's migrations
`prepareTemplate(deps)` SHALL, as the superuser of `deps.adminUrl`, create `TEMPLATE_DATABASE` owned by `ursitoare_owner` when absent; as the owner on the template (`deps.ownerUrl` with its database name) run `prepareDatabase` with `deps.clock` (default the system clock) and `prepareDurable` (console silenced); end every other session on the template; and answer `{ created, applied }`, `applied` the migrations `prepareDatabase` applied. A failure SHALL reject with `ResetError` at step `template`, `reason` the SQLSTATE or code, message `reset failed at step template (<reason>)`; with the owner role missing no template database remains.

#### Scenario: Create, repeat, a template one migration behind, and refusals
- **WHEN** on a fresh embedded cluster with the roles and the database `ursitoare` (owner password `OW`, 64 `o`), `prepareTemplate` runs twice; after the owner deleted the ledger row of version 550 and revoked `UPDATE (auth_scheme, header_name)` on `ursitoare.credential_ref` from `ursitoare_app` on the template; with a wrong owner password; on a template where the superuser created schema `dbos` first; and on a second fresh cluster without the roles; stdout and stderr are captured throughout

### Requirement: resetEngineDatabase recreates the engine database from the template and waits for the engine
`resetEngineDatabase(deps)` SHALL, as the superuser on the maintenance database, run `DROP DATABASE IF EXISTS "ursitoare" WITH (FORCE)` and `CREATE DATABASE "ursitoare" OWNER "ursitoare_owner" TEMPLATE "ursitoare_template"` (on `55006` end the template's sessions and retry once), then poll `GET <engineOrigin>/health` every `healthPollMs` (default 1000) until it answers 200 with `checks.db` `"ok"`, and answer `{ engineRestarted }`, true when a poll failed before the first success. It SHALL give up when a failed poll ends at or after `healthTimeoutMs` (default 180000). `reset.ts` SHALL hold neither `keycloak`, `vault` nor `docker`. A failure SHALL reject with `ResetError` at step `drop`, `create` or `health` (reason the SQLSTATE, or `timeout`), message `reset failed at step <step> (<reason>)`.

#### Scenario: Recreate, a restart, a silent engine and refusals
- **WHEN** on a fresh embedded cluster holding a migrated `ursitoare` with a table `ursitoare.reset_marker`, a connected owner pool, a database `keycloak` with one row and an open session, and a prepared template, `resetEngineDatabase` runs against a health server answering 200 `{"status":"ok","version":"x","checks":{"db":"ok"}}`; against one answering 503 twice; against one answering 503 always (`healthTimeoutMs` 300); with a wrong superuser password; and `reset.ts` is read
- **THEN** the first answers `{ engineRestarted: false }` after one health request; `to_regclass('ursitoare.reset_marker')` is null, the owner pool answers `SELECT current_user` with `ursitoare_owner` on its first or second attempt, the ledger has `N` rows, the `keycloak` database has the same `oid` and its row and a session still answering `SELECT 1`; the second `{ engineRestarted: true }` after three requests; the third rejects with `ResetError`, step `health`, reason `timeout`, message `reset failed at step health (timeout)`, after two or more requests; the fourth step `drop`, reason `28P01`; the source holds none of the three words

### Requirement: An interrupted reset recovers at the next start
A reset killed between its two statements leaves no `ursitoare`; `db-roles` SHALL then create it, `db-prepare` migrate it, `prepareTemplate` rebuild the template and `resetEngineDatabase` replace it.

### Requirement: The reset entry reads its settings from files and reports one outcome
`stackResetDeps(dir)` SHALL answer the stack's `ResetDeps`: `adminUrl` the compose file's admin URL on the database `postgres`, `ownerUrl` its owner URL, `engineOrigin` `http://ursitoare:8080`, the passwords from `<dir>/secrets/db_superuser_password` and `db_owner_password`, newline removed. `resetMain(argv, io, opts)` SHALL, for `["--prepare"]`, run `prepareTemplate` then `resetEngineDatabase`, write `template: <created|present>; migrations applied: <n>` and `reset: engine database recreated; the engine <restarted|stayed up>` and answer 0; for `["--wait"]`, run `waitForEngine`, write `engine: healthy` and answer 0; for a `ResetError` at `health` write its message to `io.stderr` and answer 3, at another step answer 1; for any other failure write `reset failed: the settings could not be read` and answer 1; for any other `argv` write `usage: reset.ts --prepare | --wait` and answer 64. `opts.deps` replaces fields of the built `ResetDeps`; no password is written.

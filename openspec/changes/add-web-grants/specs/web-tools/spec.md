## Purpose

A tenant admin reads tool servers and their surfaces, approves a surface, lists, creates, revokes and re-confirms grants, and validates and deploys the tenant's policy in the browser.

## ADDED Requirements

### Requirement: A tool server is parsed strictly, read as a row and explained by its state
`parseToolServer` SHALL return a `ToolServerView` for an object whose members match design.md § Parsing and `null` for anything else. It SHALL keep, per tool, `untrusted_result` (absent: true), `unsafe_to_retry` (absent: false) and `http` from the answer's `pendingSurface`, else its `approvedSurface`, ignore every other member the view does not hold, read an absent `pendingSubmittedBy` as `null` and not change its input. `serverRowText` SHALL give `${id} · ${origin} · ${state}`, `toolRows` one `{ name, effect, block, result, call }` per tool (`block` the ref or "—", `result` "untrusted" or "trusted", `call` `<method> <path>`, "—" when the answer holds no surface), and `stateNote` a text naming the short digests for `pending` and `drifted` and `null` for `approved`.

#### Scenario: Tool servers are parsed, ignored members stay out and the texts are fixed
- **WHEN** `parseToolServer` gets `RAW`, `APPROVED` and the 21 malformed values of test-plan.md § Tool servers; `serverRowText`, `toolRows` and `stateNote` run on `VIEW`, `APPROVED`, `NOSURF` and `VIEW` drifted
- **THEN** `RAW` gives `VIEW` (each tool's members from `pendingSurface`, no `local`, `registeredAt`, `approvedSurface` or `pendingSurface` key) and stays unchanged; `pendingSubmittedBy` is `"u_carol"`, `"u_dave"` when `RAW` has it and `null` without the member; `APPROVED` (nothing pending) has `pendingSubmittedBy` `null` and the refs; each malformed value gives `null`; the row text is `acme · https://tools.fake.test · pending`; the tool rows and the three notes (`APPROVED` has none) are those of the plan

### Requirement: Approval compares the approver with the pending surface's submitter under the tenant's review profile
`approvalView(s, me)` SHALL return `{ canApprove: false, selfApproval: false, message: "Nothing to approve." }` when `s.pendingDigest` is null; else, when `s.pendingSubmittedBy` equals `me.userId`, `{ false, false, "Another admin must approve this surface." }` for `team` and `{ true, true, <a note that approving is recorded as a self-approval> }` for `solo`; else `{ true, false, null }`. It SHALL never read `registeredBy`; a submitter the answer does not name blocks nobody, because the engine decides (422 `approver_is_submitter` or `self_approval_required`, U47).

#### Scenario: Nothing pending, team, solo, drifted and an unknown submitter
- **WHEN** `approvalView` runs on the rows of test-plan.md § approvalView rows with `me` `u_carol`
- **THEN** every row gives the table's triple: `NONE` nothing to approve; `MINE` (registrar `u_erin`) blocked in a team and a self-approval in a solo tenant; `OTHER` (submitter `u_dave`), `DRIFT` and `UNKNOWN` (no submitter in the answer) `true`, `false`, `null`

### Requirement: An approval is requested explicitly and its refusals are explained
`approveRequest(s, me, { ticked, ownSurface })` SHALL refuse with the `approvalView` message when `canApprove` is false, refuse with 'Tick "I approve my own surface" to approve a surface you submitted.' when the box is shown (`selfApproval` of the view, or `ownSurface`) and `ticked` is false, and otherwise return `{ ok: true, body: { digest: s.pendingDigest, selfApproval } }`, `selfApproval` being true exactly when the box is shown. `approveDialog` SHALL give the title `Approve surface <12 characters after sha256:>?`, a description naming the server and the action "Approve surface" (`null` with nothing pending). `approveFailure` SHALL give the `toolsErrorMessage` and `ownSurface` true exactly for the reason `self_approval_required`. `toolsErrorMessage` SHALL give the text design.md § Messages lists for the reason of a 422 `OPERATION_REFUSED`, else the kit's text for the code, and append " Decision id: <id>" to a 403 that carries one.

#### Scenario: Requests, dialog and failure texts
- **WHEN** `approveRequest`, `approveDialog` and `approveFailure` run on the rows of test-plan.md § Approval requests
- **THEN** `MINE` solo unticked gives the Tick message, ticked `{ ok: true, body: { digest: DP, selfApproval: true } }`; `UNKNOWN` solo gives `selfApproval: false`, with `ownSurface` true the Tick message unticked and `selfApproval: true` ticked; a team `MINE` and `NONE` give the `approvalView` messages; the dialog is `Approve surface 0123456789ab?` (`null` for `NONE`), `SURFACE_APPROVED` "Surface approved."; the failure rows are the table's, `ownSurface` `true` only for `self_approval_required`

### Requirement: A grant is parsed, read as a row and offers the actions its status allows
`parseGrant` SHALL read a list item `{ grant, status }` (U49's `listGrants` item; the record with `status` beside it is malformed) into `{ id, subject, tool, scope, status }` (subject `role <name>` or `user <id>`; scope `any step` or `<flow> / <node>`) and return `null` for anything U49's API cannot return: a `status` other than `active`, `needs_reconfirm` or `revoked`, an id, tool, role, user id, flow id or node id outside design.md § Parsing, a subject or scope of another `kind` or missing a member. It SHALL ignore the record's other members. `grantRowText` SHALL give `${subject} · ${tool} · ${scope} · ${status}`; `grantActions` SHALL allow revoke unless the status is `revoked` and confirm only for `needs_reconfirm`.

#### Scenario: Each subject and scope, the list item and the malformed items
- **WHEN** `parseGrant`, `grantRowText` and `grantActions` run on the rows of test-plan.md § Grants and its 17 malformed values
- **THEN** the item `{ grant: REC(), status }` gives role `author`, scope `pay-run / pay`, `needs_reconfirm`, and the flat `{ ...REC(), status }` gives `null`; the user item gives subject `user u_bob`, scope `any step`; the boundary role and user rows give their views; views, row texts and actions are the table's; `GRANT_DONE` is `{ created: "Grant created.", revoked: "Grant revoked.", confirmed: "Grant confirmed for the newest version." }`; each malformed value gives `null`

### Requirement: A grant draft becomes the API body or names the field to fix
`grantBody` SHALL trim the subject, flow and step, check in order the subject, the tool (U49's stored-tool pattern `^[a-z][a-z0-9._-]*@(0|[1-9][0-9]{0,8})$`, at most 128 characters: `add-grants-model` test-plan.md:59, the same as `parseGrant`) and, for the scope `node`, the flow and the step against the patterns of design.md § Parsing, and return the first failure as `{ ok: false, field, message }` with `field` `subject`, `tool`, `flowId` or `nodeId` (the form's field names). Otherwise it SHALL return `{ ok: true, body }` with `body` `{ subject: { kind: "role", role } | { kind: "user", userId }, tool, scope: { kind: "any_step" } | { kind: "node", flowId, nodeId }, args: [] }`; for `any_step` the flow and step are ignored.

#### Scenario: Role, user and node drafts and the refused fields
- **WHEN** `grantBody` runs on the rows of test-plan.md § grantBody
- **THEN** the bodies are `ROLE_ANY`, the user body (subject `{ kind: "user", userId: "u_bob" }`) and the node body (scope `{ kind: "node", flowId: "pay-run", nodeId: "pay" }`); a bad flow under an any-step scope is ignored; the tool `acme.lookup_vendor@999999999` gives its body, `acme.lookup_vendor@1000000000` and `acme.lookup_vendor@01` each the field `tool` with "Choose a tool from the list."; each refusal names its field (`subject`, `tool`, `flowId` or `nodeId`) with the table's message

### Requirement: Loading, failure, empty, busy and approve states are decided by pure models, not by the pages
`regionState(load, isEmpty?)` SHALL give `{ view, actionsDisabled }`: `loading` and `error` with `actionsDisabled` true; `ready`, or `empty` when `isEmpty(value)` (a policy not yet deployed is empty and can still be deployed), with it false; another phase is a `RangeError`. `actionState(a)` SHALL give `disabled` true only while `busy`, and for `done` or `failed` a `status` `{ role: "status" | "alert", text }`; an empty text or another phase is a `RangeError`. `approveControl(s, me, busy)` SHALL be disabled, without message or self-approval, while `s` or `me` is null; else it is `approvalView(s, me)` with `disabled` true when `busy` or not `canApprove`.

#### Scenario: Region, action and approve-control states
- **WHEN** `regionState`, `actionState` and `approveControl` run on the rows of test-plan.md § Page states
- **THEN** loading and error give `actionsDisabled` true; a server with tools, one without and an undeployed policy give `ready`, `empty`, `empty` with it false; idle, busy, done and failed give the table's four results; the approve control is disabled for no server, no session, a team submitter, nothing pending and a request in flight, and enabled otherwise (`selfApproval` true only for the solo submitter); an unknown phase and an empty text are `RangeError`

### Requirement: The calls use the right routes and headers and refuse unreadable answers
`loadToolServer`, `approveToolSurface`, `loadToolRefs`, `postGrant`, `revokeGrantById`, `confirmGrantById`, `loadPolicy`, `validatePolicy` and `deployPolicy` SHALL call the client with the paths, bodies and options of test-plan.md § Calls (paths without `/api/v1`); only `postGrant` and `deployPolicy` send an `Idempotency-Key` header, and the confirm sends `{}`, which means the newest version. An id outside its pattern, a blank key and an invalid draft SHALL throw `RangeError` before a call; an answer a parser refuses SHALL reject with `ApiRequestError` status 200, code `INVALID_RESPONSE`. `loadToolRefs` SHALL return the refs of the bound blocks of `GET /blocks`, in the order read, following `next_cursor` for at most 10 pages of 100; when the tenth page still has a non-null `next_cursor` it SHALL stop and resolve with the refs read so far, never reject for that reason and give no sign that the list is incomplete.

#### Scenario: Calls of the three pages

- **THEN** the records are those of test-plan.md § Calls (eight, one per call; only `postGrant` and `deployPolicy` carry `{ headers: { "Idempotency-Key": "k-1" } }`); `loadToolRefs` returns `["acme.lookup_vendor@1", "acme.create_payment@1"]` over two requests (`{ limit: 100 }`, then `{ limit: 100, cursor: "c1" }`) and, for a cursor that is never null, makes 10 requests and resolves `acme.t1@1` to `acme.t10@1`; `validatePolicy` returns `{ ok: false, problems: [{ stage: "parse", ids: [], message: "unexpected end of input" }] }` and `deployPolicy` `V`; the `RangeError`s and `INVALID_RESPONSE` rejections are those of the plan

### Requirement: The policy view, validation and deployment read as fixed texts
`parsePolicyView` SHALL read `{ current, pendingGrants }` into `{ version, source, pendingGrants }` and return `null` for a `pendingGrants` that is not a non-negative safe integer, or a `current` that is neither null nor `{ version, source }` with a 64-hex version and at most 65,536 code points. `validationText`, `deployText`, `currentText` and `pendingText` SHALL give the texts of test-plan.md § Policies (`validationText` joins the problems with `; `, each as `<stage>`, then ` <ids joined by ", ">` when there are ids, then `: <message>` when the message is not empty, after "Not valid: "; a problem without a string `message` is malformed); `checkPolicySource` SHALL refuse more than 65,536 code points; `policyErrorText` SHALL show a `policy_invalid` refusal through `validationText` (its problems read strictly) and any other error through `toolsErrorMessage`.

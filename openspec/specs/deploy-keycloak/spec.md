# deploy-keycloak Specification

## Purpose
The base Keycloak realm of the hobbyist stack and the script that gives Keycloak its database. The realm is a template: U59's compose file hands Keycloak six values in its environment and Keycloak substitutes them at `start --import-realm`. It binds a one-page browser flow, defines the organization, the groups, two clients and the first user, and is meant to emit the claims the engine reads and the fake OIDC contract asserts. At M8 only the first user's group `ursitoare-admins` has an effect (the first user becomes `tenant_admin` through `admin bootstrap-admin`); `ursitoare-authors` and `team-default` map to nothing until U81. Every SHALL is about the files and pure checks of this unit and is decided by a Node test; what real Keycloak and Postgres do with the files is proved only by the delegate's stack run (`test-plan.md` § STACK-ONLY) and is no scenario.

## Requirements

### Requirement: The realm template takes its values from six placeholders
`deploy/keycloak/import/ursitoare-realm.json` SHALL be one JSON document whose only variable text is `${NAME}` or `${NAME:default}` placeholders, six names in all. `realmPlaceholders(template)` SHALL return each placeholder name once, sorted. `renderRealm(template, env)` SHALL make one pass over the text: `${NAME}` becomes `env[NAME]` when `env` has `NAME` as an own property (an empty string included) and stays as written otherwise; `${NAME:default}` becomes the default when `env` has no own `NAME`; the result is parsed as JSON, and invalid JSON throws `SyntaxError`. `readRealmTemplate(path?)` SHALL return the UTF-8 text of `path`, or of `REALM_TEMPLATE_PATH` under the repository root, and throw the file system's error for a missing file.

- **THEN** the constants are `deploy/keycloak/import/ursitoare-realm.json`, the six names of `KC_REALM_ENV` in the order of `design.md` § Interfaces, `["ursitoare-admins", "ursitoare-authors", "team-default"]`, `["ursitoare-engine", "ursitoare-mcp"]` and `browser-single-page`; the first read answers `{"a":1}` and the second throws an error whose `code` is `ENOENT`; the names are `["A", "B", "E"]`; the renders are `{ a: "1", b: "", c: "", d: "" }`, `{ a: "x", b: "${B}" }` and `{ a: "x" }`; the last two throw an error named `SyntaxError`

### Requirement: The realm holds the organization, the groups, two clients and the first user
The template SHALL have realm `ursitoare`, `enabled` true, `sslRequired` `external`, `registrationAllowed` false, `organizationsEnabled` true, no `clientScopes` key, and the browser flow of the next requirement. `groups` SHALL be `ursitoare-admins`, `ursitoare-authors` and `team-default`. `ursitoare-engine` SHALL be confidential with the secret placeholder, standard flow on, implicit, direct access and service accounts off, one exact redirect URI, PKCE `S256`, `post.logout.redirect.uris` holding the sign-in URI and then the redirect URI joined by `##`, default scopes `web-origins`, `acr`, `profile`, `roles`, `basic`, `email`, optional scope `organization`, and one `oidc-group-membership-mapper` (`claim.name` `groups`, `full.path` `"false"`, `"true"` for ID token, access token and userinfo). `ursitoare-mcp` SHALL be public with standard flow, PKCE `S256`, the redirects `http://127.0.0.1/*` and `http://localhost/*` and an `oidc-audience-mapper` for the audience `ursitoare-mcp` on the access token. `users` SHALL hold one user: the first-user placeholder as name, one password credential from the password placeholder with `temporary` true, the group paths `/ursitoare-admins`, `/ursitoare-authors`, `/team-default`, and no `firstName`, `lastName` or `email`. `organizations` SHALL hold one enabled organization whose `name` and `alias` are `${KC_URSITOARE_ORGANIZATION:home}`, with the first user as its only member.

### Requirement: The realm binds a one-page browser flow
The template SHALL define exactly three authentication flows and bind `browserFlow` to the first. `browser-single-page` (top level, `basic-flow`) SHALL hold `auth-cookie` ALTERNATIVE (priority 10), `identity-provider-redirector` ALTERNATIVE (25) and the sub-flow `browser-single-page forms` ALTERNATIVE (30). That sub-flow SHALL hold `auth-username-password-form` REQUIRED (10) and the sub-flow `browser-single-page otp` CONDITIONAL (20). That sub-flow SHALL hold `conditional-user-configured` REQUIRED (10) and `auth-otp-form` REQUIRED (20). No execution reachable from the bound flow SHALL have the authenticator `organization`.

#### Scenario: The bound browser flow has no organization step
- **WHEN** the rendered template's `browserFlow` and `authenticationFlows` are read
- **THEN** `browserFlow` is `browser-single-page`; the flows' aliases are `["browser-single-page", "browser-single-page forms", "browser-single-page otp"]` with `topLevel` true, false, false; the executions, as `[authenticator or flowAlias, requirement, priority]`, are `[["auth-cookie","ALTERNATIVE",10], ["identity-provider-redirector","ALTERNATIVE",25], ["browser-single-page forms","ALTERNATIVE",30]]`, `[["auth-username-password-form","REQUIRED",10], ["browser-single-page otp","CONDITIONAL",20]]` and `[["conditional-user-configured","REQUIRED",10], ["auth-otp-form","REQUIRED",20]]`; no execution has the authenticator `organization`; every `flowAlias` names a defined flow

### Requirement: realmClaimProblems lists each way the realm could stop emitting what the engine reads
`realmClaimProblems(realm)` SHALL answer `[]` for a rendered realm that holds every fixed value of the two previous requirements, and otherwise one text per broken rule, in the rule order and with the texts of `test-plan.md` § Rule texts. A value that is not a record SHALL answer `["realm: not an object"]`. A missing client SHALL skip that client's other rules, and a realm without exactly one user with a name SHALL skip the user and organization rules. A string anywhere in the realm that still holds `${` SHALL give `realm: unresolved placeholder at <path>`. It SHALL never throw.

#### Scenario: Each broken rule gives its own problem
- **WHEN** `realmClaimProblems` runs on the template rendered with `ENV` and rendered without `KC_URSITOARE_ORGANIZATION`, and then on each of the 30 mutations of `test-plan.md` § Mutation rows applied one at a time to a fresh copy of the realm rendered with `ENV`
- **THEN** the first two answers are `[]`; each mutation answers exactly the row's list, for example `["realm: sslRequired is not external"]` for `sslRequired` `none` and, for a wildcard engine redirect, `["client ursitoare-engine: redirectUris is not one exact URI", "client ursitoare-engine: post.logout.redirect.uris is not one exact URI followed by the redirect URI"]`; every row of the table holds

### Requirement: The realm's claims have the shape the fake OIDC contract and the engine expect
The claims the realm's mappers and scopes are set up to put in the first user's ID token SHALL have the shapes `test/support/fake-oidc` emits and `oidcContract` asserts: `groups` an array of plain group names (none starting with `/`), `organization` a one-entry array holding the organization's alias, asked for through the optional scope `organization` (as the fake emits it only for that scope), and the profile claims `name`, `email` and `preferred_username` from the `profile` and `email` scopes. The engine's `groupsFromIdToken` and `organizationFromClaim` SHALL accept them. The realm's client ids and their public or confidential kind SHALL equal the fake's.

#### Scenario: The realm's claims have the fake's shapes and the engine reads them
- **WHEN** a fake OIDC (`startFakeOidc`, loopback port 0, closed in `t.after`) mints ID tokens for `carol` with the default scope and with the scope `openid profile email`, and the payload the realm rendered with `ENV` is set up to give the first user is built as `{ groups: <the user's group paths without the leading "/">, organization: [<the organization's alias>] }`
- **THEN** the fake's `carol` token has `groups` `["ursitoare-admins"]`, `organization` `["org-a"]` and string `name`, `email` and `preferred_username`, and the token for `openid profile email` has no `organization` key; the realm's engine client lists `organization` only under `optionalClientScopes`, lists `profile` and `email` under `defaultClientScopes`, and its groups mapper has `claim.name` `groups`; the derived payload is `{ groups: ["ursitoare-admins", "ursitoare-authors", "team-default"], organization: ["home"] }`; the shape test of `test-plan.md` § Fixtures holds for the fake's `carol` and `alice` tokens and for the derived payload; `groupsFromIdToken` answers `["ursitoare-admins"]` for the fake's token and the three names for a token carrying the derived payload; `organizationFromClaim(["home"])` answers `home`; `bootstrapAdminGroup({})` equals `REALM_GROUPS[0]`; `REALM_CLIENTS` equals the fake's `CLIENTS` ids and each realm client's `publicClient` equals `!confidential`; `realmClaimProblems` answers `[]` for the realm rendered with `ENV`

### Requirement: The realm values come from the first-run files
The three placeholders that U57's `init-secrets` fills (`KC_URSITOARE_CLIENT_SECRET`, `KC_URSITOARE_FIRST_USER`, `KC_URSITOARE_FIRST_PASSWORD`) SHALL be keys of its `.env` (`ENV_KEYS`), and the other three names of `KC_REALM_ENV` SHALL be the ones the compose environment supplies. A realm rendered from the `.env` that `planSecrets` plans, plus those three values, SHALL have no problem, and carry the same texts as the secret files.

### Requirement: Keycloak's role and database are created from the secret file
`deploy/postgres/initdb/10-keycloak.sh` SHALL be a bash script that, through `psql -v ON_ERROR_STOP=1` as `$POSTGRES_USER` on the database `postgres`, creates the role `keycloak` (`LOGIN` and no other attribute) with the password that psql reads itself from `/run/secrets/db_keycloak_password`, and the database `keycloak` owned by `keycloak`, and runs no other statement. It SHALL put the password on no command line, in no environment variable and in no output of the script, and SHALL neither `exit` nor change shell options (the image may source the file).

#### Scenario: The init script creates exactly the role and database from the secret file
- **WHEN** `existsSync` is asserted for the script and its text is read
- **THEN** its first line is `#!/bin/bash`; the statements are exactly `CREATE ROLE keycloak LOGIN PASSWORD :'kc_password';` and `CREATE DATABASE keycloak OWNER keycloak;`; the line `\set kc_password `cat /run/secrets/db_keycloak_password`` is the only reference to `/run/secrets/`; the psql line is `psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname postgres <<'SQL'`; the checker `scriptProblems` answers `[]`

#### Scenario: Each deviation of the init script gives its own problem
- **WHEN** each of the 11 edits of `test-plan-data.md` § Script rows is applied to the committed text and `scriptProblems` runs on it
- **THEN** the answer is exactly the row's list: for example a literal password gives the statements text and the secret-file text; removing `-v ON_ERROR_STOP=1` gives `script: psql is not run with -v ON_ERROR_STOP=1`; adding `exit 0` gives `script: changes shell options or exits`; every row of the table holds

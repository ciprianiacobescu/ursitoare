# web-runs Specification

## Purpose
The run pages let a signed-in user list runs, follow one run on a timeline of its steps with their inputs and outputs, and start a mocked test run from the flow editor; the closing journey of M4 proves it in a browser.

## Requirements

### Requirement: Run views are parsed strictly and read through four loaders
The web app SHALL parse the `RunView`, `StepView` and `PayloadView` of the runs API, rejecting any answer that does not fit, and read the run list, a run, its steps and a payload through `runListFetcher`, `loadRun`, `loadSteps` and `loadPayload`; a failing list SHALL leave the kit table's retry button "Try again".

#### Scenario: Views are parsed strictly
- **WHEN** `parseRunView(RUN)`, `parseStepView(STEPS[2])` and `parsePayloadView({ sha256: D("4"), mediaType: "application/json", size: 38, data: { payment_id: "P-1" } })` run; `parseRunView` gets `RUN` with `state: "paused"`, no `ownerTeam`, `principal.kind: "robot"`, `error: { code: "X" }`, a 63-character `inputRef`; `parseStepView` gets `STEPS[2]` with `seq: -1`, `taint: [1]` and `state: "done"`; `parsePayloadView` gets `size: -1` and no `data`; `parseRunView` gets `RUN` plus `extra: 1`
- **THEN** the valid inputs give values deep-equal to them, `principal`, `error` and `taint` being copies; every invalid input gives `null`; `extra: 1` is dropped

#### Scenario: Loaders call exactly the run routes
- **WHEN** a recording client serves `runListFetcher(client)` with `{ cursor: null, limit: 50, signal }` then `{ cursor: "c1", limit: 50, signal }`, answered `{ items: [RUN], next_cursor: "c1" }` then `{ items: [{ ...RUN, state: "paused" }], next_cursor: null }`; `loadRun(client, "run_1", signal)` and of `"bad id"`; `loadSteps(client, "run_1", signal)` answered `{ items: [STEPS[0], STEPS[1]], next_cursor: "c1" }` then `{ items: [STEPS[2], STEPS[3]], next_cursor: null }`, and a `loadSteps` whose client answers a new cursor forever; `loadPayload(client, "run_1", D("3"), signal)` (the input of `pay`), `loadPayload(client, "run_1", D("4"), signal)` and of a short digest; the kit's `createCursorList(runListFetcher(client))` loads against a client whose `get` rejects `ApiRequestError(500, "INTERNAL", "m")`, then `retry()` against it now answering `{ items: [RUN], next_cursor: null }`, `tableView` read after each
- **THEN** the list calls are `{ path: "/runs", opts: { query: { limit: 50 }, signal } }` then the same with `cursor: "c1"` in the query; the first page is `{ items: [RUN], next_cursor: "c1" }`, the second rejects with `ApiRequestError` of status 200, code `INVALID_RESPONSE`; `loadRun` makes exactly `{ path: "/runs/run_1", opts: { signal } }` and returns `RUN`; the step and payload calls are those of reference.md § Calls, giving `{ steps: STEPS, truncated: false }`, the endless one called 5 times with `truncated: true`, and the parsed input and output payloads; the bad id and digest reject with `RangeError` without a call; after the failure `tableView` gives `retry` `again`, `retryLabel` `Try again`, `showError` true; after the retry the state is `loaded` with `[RUN]` and `retryLabel` is null

### Requirement: Step renderers are registered by node kind
`registerStepRenderer` SHALL add a renderer for one node kind, and `stepRendererFor` SHALL return it, or a default renderer for a kind nobody registered, with `stepRenderers.list()` holding the built-ins `block`, `switch`, `wait` and `end` first.

#### Scenario: Built-ins, a default, registration and refusals
- **WHEN** `stepRenderers.list()` is read; `stepRendererFor` gets `"block"`, `"switch"`, `"wait"`, `"end"`, `"mystery"` and `"__proto__"`; `registerStepRenderer` gets `{ kind: "llm.extract", label, details }` and the lookup and list are read again; then it gets `llm.extract` and `block` again and the seven `BAD_RENDERERS` (reference.md § Fixtures)
- **THEN** the first list has the kinds `["block", "switch", "wait", "end"]` and each lookup returns the object in the list; the other two kinds give one default renderer, `kind` `"*"`, whose `label(STEP(0, "x", "mystery"))` is `"mystery (unknown kind)"` and `details` gives `[]`; after the registration the lookup returns the registered object and the kinds end with `"llm.extract"`; the two repeats throw `StepRendererError` with `code` `STEP_RENDERER_DUPLICATE`, the seven bad ones `STEP_RENDERER_INVALID`; each refusal leaves the list unchanged

### Requirement: The timeline shows every step with its state, details and payload
`stepStateLabel`, `timelineItems` and `stepDetailRows` SHALL list a run's steps in `seq` order, label a `started` step of a terminal run (whatever its state) "Interrupted" with the note "Not finalized" and never running, show a mocked `wait` with outcome `skipped`, and link a decision only when `policyDecisionId` is set; `payloadShown` SHALL show a payload only as the text of what was loaded, and `setPayloadLoad` SHALL confine a payload failure to its own digest.

- **THEN** the first items are `{ seq, nodeId, text }` for `lookup`, `route`, `pay`, `done` (seq 0 to 3) with the texts `"block · completed"`, `"switch: active · completed"`, `"block · completed"`, `"end · completed"`; `stepStateLabel` gives `{ label: "Interrupted", note: "Not finalized" }` for `started` with `completed`, `failed`, `cancelled`, `{ label: "running", note: null }` for `started` with `queued`, `running`, and `{ label: <the state>, note: null }` for the other 15 pairs; the started step reads `"block · running"` for `"running"` and `"block · Interrupted (Not finalized)"` for the other three; `nap` reads `"wait: skipped · completed"`; the rows for `STEPS[2]` are `PAY_ROWS` (reference.md § Fixtures); the failed `pay` step's rows end as `PAY_FAILED_TAIL` (reference.md § Fixtures); the started step's State row is `Interrupted (Not finalized)`; `decisionHref("a b")` is `null`; `runErrorText` gives `"E_X: failed"`, `"E_X: failed (at pay)"` and `null`; `payloadShown` gives `"none"`, `{\n  "payment_id": "P-1"\n}`, and `"That item does not exist, or you cannot see it."`; `setPayloadLoad` returns a new Map with the same ready object for `D("3")` and the error load for `D("4")`, `LOADS` unchanged, and `payloadShown` of the two gives `{\n  "vendor_id": "V-1"\n}` and the NOT_FOUND text (plain text in that block, no alert)

### Requirement: Polling follows a run until it ends
`nextPollDelay` SHALL give the wait before the next look at a run (250 ms doubling to 2,000 ms, none once terminal), and `followRun` SHALL reload the run and its steps after each wait until the run is terminal, passing every snapshot to `onUpdate`, within a deadline; a failed poll SHALL show the `ErrorPanel` and the button "Try again", keep the earlier snapshot, stop polling and restart only on that button, and a malformed run id (a `RangeError`) SHALL show the 404 panel "Not found" without a request.

#### Scenario: Delays, a followed run, a deadline and failures
- **WHEN** `nextPollDelay` gets `("queued", 0)`, `("running", n)` for n = 0, 1, 2, 3, -1, NaN, and `("completed", 0)`, `("failed", 7)`, `("cancelled", 0)`; `followRun(client, "run_1", { sleep, now, deadlineMs: 20000, onUpdate })` runs against a client that answers `/runs/run_1` with `queued`, `running`, `running`, `completed` in turn and `/runs/run_1/steps` with 0, 1, 2 and 4 steps, a `sleep` that records its delay and resolves, and `now` returning 0; then against a client that always answers `running` with `now` returning 0, 6000, 12000, 18000, 24000 in turn; `followRun`, `loadRun(client, "bad id!")`, `failureView` and `runPageView` run on the six failure cases of reference.md § Failures
- **THEN** the delays are 250, 250, 500, 1000, 2000, 250, 250 and `null` three times; the first follow resolves with the last snapshot (`completed`, the 4 steps), `sleep` got `[250, 500, 1000]`, `onUpdate` got the four states in order, and the client was asked `/runs/run_1` and `/runs/run_1/steps` alternately, four times each; the second rejects with `RunFollowError` of `code` `RUN_FOLLOW_TIMEOUT`, `sleep` having got `[250, 500, 1000]`; each failure case has the outcome of reference.md § Failures, strictly equal

### Requirement: A step carries its hook trace, parsed strictly
`parseStepHooks` SHALL return `undefined` for `undefined`, `null` for anything that is not `{ inputOriginalRef, entries }` with `inputOriginalRef` null or 64 lowercase hex digits and at most 64 entries of eleven valid members (`label` matching `^(pre|post):(rule\.)?[a-z][a-z0-9_]{0,127}$`, `kind` `code` or `block`, `fused` boolean, `attempt` an integer of 1 or more, `state` `completed` or `failed`, `action` null or one of `continue`, `skip`, `redirect`, `retry`, `fail`, `mutated` null, `input` or `output`, `to` null or a string matching `^[a-z][a-z0-9_]{0,127}$` (the store's `NODE_ID_PATTERN`, `src/runs/store/validate.ts:22`, restated web-side; any other value makes the trace malformed), `error` null or `{ code, message }` of strings, `tool` null or a text of 1 to 256 characters, `idemKey` null or `ik1_` and 64 hex digits), and otherwise the copy; `parseStepView` SHALL keep a valid `hooks` as the last member of the view, keep a malformed one as `hooks: null` (the last member too) without refusing the step, and add no key for a step without one (`StepView.hooks` is `StepHooksView | null`: `null` means malformed, an absent key means no trace).

#### Scenario: Absent, valid and malformed hook traces
- **WHEN** `parseStepHooks` gets `undefined`, `{ inputOriginalRef: null, entries: [G, N] }`, 64 copies of `G`, `T("review")`, `T("a".repeat(128))` (`T` of `test-plan.md` § Step fixtures), and nineteen malformed values (`null`, a string, an array, no `entries`, `entries` an object, a 2-character ref, label `guard`, kind `llm`, attempt 0, attempt NaN, action `explode`, an entry with only a label, 65 entries, error `{ code: 1 }`, idemKey `ik1_x`, and `T` of `"Review"`, `"a".repeat(129)`, `""` and `5`); `parseStepView` gets `STEP`, `STEP` plus the valid `hooks`, and `STEP` plus `hooks: { entries: 5 }`
- **THEN** the results are `undefined`, a deep copy of the input (not the same objects), 64 entries, a deep copy of each of the two `T` traces (their `to` kept), and `null` nineteen times; the first view has no `hooks` key (`"hooks" in view` is `false`); the second has the 15 keys of `STEP` followed by `hooks`, deep-equal to the input; the third has the 15 keys of `STEP` followed by `hooks` (`"hooks" in view` is `true`), its `hooks` is `null`, and its other 15 members equal the first's
